## EnemyMobile 巨型单位脚下攻击 Bug 修复
- 现象：远程单位会跑到高大的巨型单位脚底下攻击。
- 根因：`TargetData.Pos`（即 `Actor.CenterPos`）返回的是 `AimPoint`（胸口/头部高处）；`EnemyMobile` Follow/Attack 状态移动停止距离用**含高度的三维距离**且**未减目标半径**，导致巨型单位身高把距离"抬高"，永远判定"没到位"，一直往目标中心冲；而 `DetectionModule.IsTargetInAttackRange` 判定时加了 `Target.Actor.HalfRange`，所以状态机能切到 Attack 并在脚下开火。
- 修复：`EnemyMobile.cs` Follow/Attack 两处移动判定改为**水平距离（忽略 Y）+ 减去目标半径**（`m_EnemyController.Target.Actor?.HalfRange ?? 0f`）。普通小怪行为基本不变。
- 注意：`SpecUnitKei.cs`、`SimpleTurret.cs`、`GuardDog.cs` 等其它敌人移动逻辑可能也存在同类问题，未改。

## DetectionModule 增加最短转火时间
- 现象：巨像（Dec_Colossus）被围殴时因 `OnDamagedDiffuse`（受击转火）和 `CheckNewTarget`（视野转火）频繁切换目标，炮塔一直转头无法开火。
- 修改：`DetectionModule.cs` 新增 `MinSwitchTargetTime`（默认 4 秒）+ `TimeLastTargetSet`（在 SetTargetActor 成功设置新目标时记录）+ `IsSwitchingCooldown` 属性。`OnDamagedDiffuse` 和 `CheckNewTarget` 在冷却期内拒绝切换目标（当前目标无效/丢失超时后不受限，可正常转火）。
- 该字段是 public Inspector 字段，可在各敌人 DetectionModule 上单独配置（如巨型单位可调大）。
- 遗留：巨像炮塔 Y 轴瞄准偏高问题仍在排查中。

## 巨像炮塔 Y 轴瞄准偏高——真正根因与修复（2026-08-19）
- 现象：巨像炮塔 XZ 准、Y 偏高；用户实测"水平限制 limitRotation 归零就正常"。
- 真正根因：`Look()` 水平限制分支里 `barrelDir = new Vector3(chassisDir.x, barrelDir.y, chassisDir.z).normalized`。受限后的 chassisDir 是**单位水平向量(长度1)**，而原 barrelDir 水平分量长度 <1（dy≠0 占预算）。替换后归一化会**压缩 dy、改变俯仰角**——水平方向被钳制得越狠，Y 轴偏差越大。巨像 limitRotation=15 且炮塔在高处向下瞄，触发此 bug 导致炮管下压不足、弹道偏高。诊断日志 angle=0（内部自洽收敛）正好印证。
- 修复：改为**水平方向取受限后的 chassisDir + 俯仰角保持原 barrelDir**，按球坐标重建 barrelDir（与 GetLimitedVerticalDirection 同手法），含目标正上/正下方兜底。
- 排查期间临时诊断代码（DrawLine/DrawLog）已全部移除。
- 经验：**替换单位向量分量后 normalize 会改变其它分量的相对权重，水平钳制不应改变俯仰角**。查找时用过 Animator 假设（已排除）、重力修正（已排除）、发射方向（已排除）。

## EnemyMobile.AttackStop 语义修正（2026-08-19）
- 原实现 bug：Attack 状态 shoot 段有 `if (mustStop)` 停火分支，把已对准的炮塔 `TryStop`（"已对准反而停火"），且全项目无人赋值，仅 Inspector 手动勾选。
- 用户意图：**开火时停在原地**（移动站桩，不影响开火）。
- 修改：1) 删掉 shoot 段 `if (mustStop)` 停火分支，shoot 正常走 `IsAttackLocked`/`AimTargrt()` 链；2) 字段加 `[InspectorName("开火时停在原地")]` + Tooltip 注释；3) 修复 `InAttackState()` 中 `item.weapon.InAttackState()` **未判空 NRE**（巨像第 1 个炮塔是 SelfBody 无武器，勾上 AttackStop 后每帧调用 InAttackState 直接崩掉状态机 → 表现为不瞄准不开火）。
- `TryStop` 内部已有 `if (!weapon) return;` 判空，眩晕分支安全。
- 二次增强：AttackStop 现在**开火时炮塔也停转**——shoot 段新增 `else if (mustStop)` 分支，开火中跳过 `AimTargrt()/Look()`（炮塔冻结朝向），新增 `IsFireDelayPassed()`（提取自 AimTargrt 的开火延迟判定）保证正常开火。字段注释更新为"停在原地且炮塔停止旋转"。
- **Bug 修正**：最初 `mustStop = AttackStop && InAttackState()`，而 `WeaponEnemyController.InAttackState()` 的 `return (!InAutoReload && CanShoot)` 使武器"就绪未开火"也算开火状态 → 进入射程后 mustStop 恒 true → 炮塔永久冻结转不过去、永远无法开火。改为 `IsFiringNow()`（仅 `InCharging||InLasering||InShoots` 真正开火中），并删除原私有 InAttackState()。现在：发现目标→炮塔先转过去对准→开火中站桩+停转→开火结束继续追踪。

## 齐射武器"残余弹量 < 单次消耗"死锁修复（2026-08-21）
- 现象：Dec_Colossus Boss 最后一个炮塔，开火一次后永远不再开火也不换弹。
- 根因：武器 `UseManyMuzzle=true` 且 6 个发射点位 → `LogicInit` 中 `ShootCost = WeaponManyMuzzles.Count = 6`；弹匣仅 10 发。第一次射击后剩 4 发，`CanShoot = Magazine.CurrValue(4) >= ShootCost(6)` = false → 无法再射击；而 `UseMagazine` 只在弹匣打空(<=0)时才 `TryManualReload()`，剩 4 发不会触发 → **死锁**。武器 WeaponFlag=8（仅 ForceShoot，无 AutomaticReload）也不会自动恢复。
- 修复：`WeaponController.LogicTick()` 在 base.LogicTick() 后、UpdateAmmo() 前新增兜底：`!IsReloading && !HasFlag(AutomaticReload) && !InfiniteMagazine && 0 < Magazine.CurrValue < ShootCost && (InfiniteAmmo || Ammo.CurrValue>0)` 时 `TryManualReload()`。单发武器(ShootCost=1)不受影响。玩家侧 NoManualReload flag 仍会阻止（TryManualReload 内部 return）。
- 经验：**齐射武器弹匣应配成 ShootCost 的整数倍**，否则残余不足会卡死。

## WeaponController 新增"强制连射"标旗（2026-08-19）
- 需求：武器开火后松手不停，直到弹匣打空。
- 实现：`WeaponFlag` 新增 `ForceShoot = 1 << 3`（Inspector 名"强制连射(打空弹匣才停)"）。`HandleShootInputs` 开头加拦截：ForceShoot 武器连射/激光中松手时把 inputUp 改为 inputHeld（视同按住）；当 `(InShoots || InLasering) && !CanShoot`（弹匣打空）时结束连射（Laser 走 EndLaser，Automatic 清 InShoots+动画）。无限弹匣（InfiniteMagazine）永不停止。
- 适用范围：Automatic（全自动）与 Laser（激光）两类持续射击武器；Manual/Charge/Lock 不受影响（激光打空本就有 EndLaser 兜底，自动换弹 ReloadStart 里也有 InShoots=false 兜底）。
- 配置方式：武器 Inspector "武器标旗" 多选勾选即可。

## Compare 条件显示对 List 字段无效/报错——根因与修复（2026-08-19）
- 现象：`[Compare("UseManyMuzzle", 1, CompareOperate.Equal)]` 加在 `List<Transform> WeaponManyMuzzles` 上时，①UseManyMuzzle=false 列表仍显示（Compare 对"list 本身"不生效）；②列表元素绘制报 `找不到控制属性 WeaponManyMuzzles.Array.UseManyMuzzle`。
- 根因：Unity 会把数组/List 字段上的 PropertyAttribute **应用到每个数组元素**（路径 `WeaponManyMuzzles.Array.data[i]`），而不是数组字段本身 → 元素路径拼出的控制属性路径错误。
- 修复：
  1) `CustomLabelDrawer.ShouldDisplayField` 改为 `public static`，并解析数组路径：先 `IndexOf(".Array")` 去掉数组索引段再取父级，使控制字段按"数组字段所在层级"定位。
  2) `EditorOverride.cs` 新增私有 `ShouldDisplayField(SerializedProperty)`（反射取字段的 CompareAttribute + 调用静态判断），在 Body() 与 Foldout() 绘制循环中跳过不显示的字段——这样数组字段本身（列表头）也能响应 Compare 隐藏。
  3) 顺带修正 `WeaponMuzzle`/`WeaponMuzzle2` 的 Compare 语义：原 `[Compare("UseManyMuzzle")]`（默认 Greater 0 = true 时显示）与设计相反，改为 `[Compare("UseManyMuzzle", 0, CompareOperate.Equal)]`（false 时显示普通点位）。
- 效果：UseManyMuzzle=false → 只显示 WeaponMuzzle/WeaponMuzzle2；true → 只显示 WeaponManyMuzzles；不再报错。
- 经验：**字段级 PropertyAttribute 对 List/数组只作用到元素，要让数组字段本身响应条件需在自定义 Editor（EditorOverride）层做判断**。
