# 2026-08-26

## ProjectileMine.cs 地雷触发判定改造
- 将 `TryHit()` 从 `Physics.OverlapSphere` 改为 `BattleManager.Instance.FindUnits`（空间网格查询），以获得目标队伍信息做智能地雷判定。
- 关键结论（踩坑）：`FpsHelper.Hit`（爆炸伤害链路）依赖**精确 Collider**做直击判定（`TryGetComponent<I_Damagable>`）和爆炸遮蔽（`ExplosionBlocking`），`FindUnits` 只返回单位级 `I_Actor`，**不能**完全替代 OverlapSphere。但地雷是纯爆炸物（`collider=null` 不做直击），故只在触发判定环节用 `FindUnits`，爆炸逻辑由 `FpsHelper.Hit` 内部自理。
- 触发逻辑：`new PECircle(Root.position.ToVector2(), DamageOuterRadius)` + `TargetCfg.Enemy` + customFilter（`FpsHelper.VaildTarget` + `intelligent` 时 `item.Team != m_Actor.Team`），再叠加 `Vector3.Distance(actor.Pos, Root.position) < TriggerRange` 精确触发距离校验。
- 删除死代码：`IsHitValid` 方法、`k_TriggerInteraction` 常量、`m_collider` 字段及其 GetComponent 赋值。
- 命名空间：`GameContract`(PECircle/TargetCfg/I_Actor)、`Utils`(FpsHelper) 已 using，编译无错。
- **BUG 根因（重要）**：`TargetCfg.Enemy = { targetType = UnitTypeEnum.Enemy }`（`1<<2`）只匹配 `UnitTypeEnum.Enemy` 类型单位，**查不到玩家（Player，`1<<0`）**。地雷要炸玩家必须改用 `TargetCfg.EnemyAI = { targetType = All & ~Other }`（匹配所有非 Other 类型）。此坑适用于任何"用 FindUnits 找玩家/通用目标"的场景——别用 TargetCfg.Enemy 找玩家。
- 后续用户把查询半径改为 `(PEInt)TriggerRange`（不再用 DamageOuterRadius），并加了调试字段 `show = BattleManager.Instance`。
- **地雷独立伤害数据**：`ProjectileMine` 新增 `[SerializeField] private DamageData SelfDamageData`（参考 `SustainedEffect` 的自带数据模式）。`OnEnable` 里若 `SelfDamageData.IsValid()` 则赋给基类 `DamageData`（自部署/无武器来源时 DamageData 否则为 null 导致爆炸无效）；`_OnShoot` 改为 `SelfDamageData.IsValid() ? SelfDamageData : WeaponBase.Damages[1]`（优先自带，回退武器）。`DamageData` 是 `[System.Serializable] class` 实现 `IDamageData`，可序列化。
- **新地雷类 `DeployableMine`（2026-08-26 创建，规划废弃 ProjectileMine）**：`Assets/Scripts/02Game/Gameplay/Projectile/DeployableMine.cs`。纯 MonoBehaviour 自部署，不继承 ProjectileBase、不依赖武器体系。**复用预制体 `Mine.prefab` 组件**（该预制体已挂：`Actor`(type=Other=16, team=0, rangeLength=0.3)、`Health`(MaxHealth=5)、`LimitedLife`(LiftTime=360)、`Damageable`、`SphereCollider`、`Animator`、`ProjectileMine`(旧脚本, Root/TriggerRange=2)）。关键设计：`[SerializeField] DamageData DamageData`（独立伤害）+ `[SerializeField] Transform Root`；队伍从 `GetComponent<Actor>().Team` 读取（不自己带 Team 字段）；`Deploy(pos, owner)` 公开方法；触发用 `FindUnits(new PECircle(Root.position.ToVector2(), TriggerRange), TargetCfg.EnemyAI, item => FpsHelper.VaildTarget(item) && (!intelligent || item.Team != team))` + 距离校验，命中后 `m_health.Kill()`（走 Health.OnDie→Explosion，防重复爆炸）；`Health.OnDie` 订阅爆炸（被破坏也引爆）；`LimitedLife.OnEnd` 超时自毁；爆炸走 `FpsHelper.Hit`（collider=null、chargeScale=1、weapon=null、IgnoreSelf=true），`Tool.Destroy` 自毁。**注意**：`Actor.type=Other` 会被 `TargetCfg.EnemyAI(All&~Other)` 排除，故地雷不会被自身/同类查询到（不互炸），符合"反步兵地雷"定位。
- **预制体切换需手动**：新类已兼容 `Mine.prefab` 组件，但需用户手动在预制体上把 `ProjectileMine` 组件替换为 `DeployableMine` 并配置 `DamageData`（新建伤害资产）/`Root`/`TriggerRange`/`intelligent`，之后才能删除 `ProjectileMine.cs`。

## DeployableMine 贴脸巨型敌人不炸 bug（2026-08-26 修复）
- **BUG 根因**：`DeployableMine.TryHit()` 在空间网格查询（`FindUnits`，内部已用 `range.Overlaps(unit.Range)` 按单位**占位范围**相交筛选）之后，又叠加了一道 `Vector3.Distance(actor.Pos, Root.position) < TriggerRange`（0.7m）校验。`actor.Pos` = `CenterPos` = `AimPoint.position` 是单位**中心点**，地雷作为命中特效黏在巨型敌人身体表面，中心点离黏附点远超 0.7m，导致永远不满足、地雷贴脸不炸。小怪能炸是因为中心离表面 < 0.7m。
- **修复**：删除最后一道中心点距离校验，直接引爆 `FindUnits` 返回的第一个单位。空间网格的 `range.Overlaps(unit.Range)` 已是正确判定（普通地面地雷无单位占位范围覆盖时 units 为空不会误炸，敌人踩上来即引爆）。无 lint 错误。

## SustainedEffect 伤害中心锚点改造（Collider → Transform）
- `SustainedEffect.cs`（`Assets/Scripts/02Game/Gameplay/SPEffect/`）字段 `Collider`（原"根部变换"）改为 `[SerializeField] protected Transform DamageAnchor`（InspectorName"伤害中心锚点"）。
- 原因：Collider 全程只被当作位置锚点（读 `bounds.center`），从不读形状/尺寸（伤害半径来自 `DamageData`）；换成子物体空物体锚点更轻量、纯 VFX 无碰撞体也能用、避免 AABB 中心与伤害中心不一致。
- 改动点：`ApplyEffect()` 的 `pos`、`OnDrawGizmos()` 圆心、`GroundFireEffect.Activate()` 去重圆心 `_cachedCenter`，统一用 `DamageAnchor ? DamageAnchor.position : transform.position` 兜底。
- 注意：字段改名后 prefab 上旧 Collider 序列化引用丢失，需用户手动在特效 prefab 子物体挂空物体并拖到 DamageAnchor。

## EnemyMobile 敌人"跟着左右移动但不上前/乱走"bug（2026-08-26 定位+修复）
- **现象**：40 个单位时部分敌人卡在 Follow 状态不进 Attack，`SetNavDestination` 传入的是正确的玩家位置，但 Gizmos 蓝色球（`agent.destination`）显示远处旧目标(约30m外)。
- **排查排除项**：非状态机(Follow/Attack 距离判定正常)、非目标锁定(`Target.Pos`=`actor.CenterPos` 正确指向玩家)、非 MaintainMaxDis/AttackStop(均未勾)、非 Terror(没带恐惧)、非 ZergWave 初始目标(<1距离过滤干扰有限)。
- **真根因**：`PathRequestManager`（`01Manager/Battle/PathRequestManager.cs`）pending 验证阶段，把 `pathPending` 持续超过 `pathTimeout=1s` 误判为"超时"并**重试入队**。40 单位并发时 Unity 寻路排队使 pathPending 轻易超 1s → 假超时重试风暴 → 队列堆积 → 单位执行过时旧路径乱走。日志证据：`[寻路] 路径计算超时(1s)，目标 (112,26,422) agent.destination=(97,24,417)`——请求目标正确(玩家)，agent.destination 是旧路径。
- **修复**：重写 `PathRequestManager.LateUpdate` 的 pending 验证——① `pathPending` 期间**不再超时重试**（destination 已设好 agent 会朝新目标走，pathPending 只是计算中）；仅持续过久才从列表移除，不重试入队；② 只在 `pathPending=false` 后检查真正失败(`PathInvalid`/`PathPartial`单点)才做投影重试+10m兜底(保留原设计兜底能力)。
- **调试日志**：给 `RequestPath` 加 `bool log=false` 参数，`EnemyController.SetNavDestination` 把 `isImportant` 字段传给它。仅勾选该开关的单位打印 `[寻路]` 前缀日志(请求目标 vs agent.destination 对比、投影偏差、pathPending 超时等)。
- **架构重写**（同日）：用户要求重写更好的 `PathRequestManager`。新架构：① `Dictionary<NavMeshAgent, ActiveReq>` 去重——同一 agent 只保留最新请求，旧请求作废；新请求与活跃请求目标距离 < `DedupDistance=0.5f` 时忽略(去抖)；② `RequestPath` 当帧同步调 `SetDestination`(Unity 异步不阻塞，40单位级别可承受)，不再用队列+`maxRequestsPerFrame` 限量分发；③ 每帧遍历 active map，`pathPending=true` 跳过(不超时不重试)，`pathPending=false` 后只查真失败(`PathInvalid`/`PathPartial`单点)做投影重试+`FinalSampleRadius=10m`兜底；④ `verifiedOnce` 标志避免每帧反复进入失败分支；⑤ 删除 `queue`/`pendingRequests`/`maxRequestsPerFrame`/`pathTimeout`/`stable` 等旧字段，`ClearAllPending` 保留(清空 active dict)。无外部代码引用旧字段，无 lint 错误。`EnemyController.SetNavDestination` 调用点签名兼容(`RequestPath(agent, destination, isImportant)`)。
