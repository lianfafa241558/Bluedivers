## 【诊断】"子弹和人都能穿过树、别处却有空气墙"——MCP 实测结论

用 Unity MCP（实例 `Bluedivers@4a3e6a7b`，port 6400，projectRoot 已核对）在 Play 模式下读了真实状态：

### 1. 树穿模的根因：树的碰撞体压根没生成
- `TerrainCollider.m_EnableTreeColliders = 0`（**Enable Tree Colliders 没勾**）→ 地形树碰撞体是"运行时由 TerrainCollider 按 TreePrototype 复制生成"的，开关关着就一个都没有 → 在树原型预制体上加的 CapsuleCollider **完全无效**，子弹/玩家都穿
- Terrain 对象：`Terrain`，layer=3(Ground)，`preserveTreePrototypeLayers=False`（=树实例会被强制改成 Terrain 的层 Ground），`treeInstances=374`，`treePrototypes=11`
- 实例分布：`[0]=37 [1]=36 [2]=43 [3]=50 [4]=42 [5]=41 [6]=37 [7]=22 [8]=22 [9]=25 [10]=19` → 与"0-6 石块 / 7-10 树"完全吻合（石块 286 + 树 88）

### 2. 运行时层掩码（GameContract.LayerDefinition @ 01_GameContract）

| --- | --- | --- |

### 4.8 【优化分析】弹坑的"三段昂贵操作"如何省（用户确认弹坑三件事都必须做）
用户重构出 `08Map/TerrainClearer.cs`（static 门面 + 内部 `Driver` 隐藏常驻对象，`[RuntimeInitializeOnLoadMethod]` 自建）：请求队列 → 逐帧 `Dispatch` 到三条腿（`TreeDestructor` / `TerrainDetailEraser` / `RockCoverDestructor`：悬崖覆盖物 + 撤回 `TerrainUtils.AreaCircles`），然后按 `RefreshInterval=0.25s` 统一做：`TreeDestructor.Flush()` + `TerrainDetailEraser.Flush()` + `TerrainUtils.RebuildTreeColliders(Main)` + `TerrainUtils.AsyncRefresh(true)`（= `nav.UpdateNavMesh`）。语义：`ClearInRadius`=清除（忽略白名单，带 `TreePrototypeRange 7-10`/`RockPrototypeRange 0-6`）、`DestroyInRadius`=摧毁（走白名单）、`MarkTerrainChanged()`=标脏高度。
`TerrainUtils.RebuildTreeColliders` 注释里已记录**实测结论**：`SetTreeInstances` 后树碰撞体不会自动更新，只能切一次 `TerrainCollider.enabled` 强制重建（重建整张地形碰撞体+全部树碰撞体，几千棵时很贵）；且**只有 prefab 上的 CapsuleCollider 参与**，Box/Sphere 不生成树碰撞体（所以 0-6 石块即使开着开关也没有碰撞体）。

一次弹坑的真实代价分解（读 `TerrainUtils.ModifyHeightMap` 源码 + Unity 行为）：
| 步骤 | 相对量级 | 能否省/合并 |
| --- | --- | --- |
| 高度图 patch 逐格 loop（`GetHeights`→算→`SetHeightsDelayLOD`，每行按 `maxTimePerFrame=0.01s` 让出）| 小~中（∝R²，已分帧） | 无法省 |
| `data.SyncHeightmap()`（延迟写入的"生效点"，触发地形网格/LOD 更新）| **大** | **可合并：一帧 N 坑只 Sync 一次** |
| `ModifyAlphaMap`（逐 patch `SetAlphamaps`）| 中 | 无法省，但别额外 Flush |
| 树实例整表提交 `SetTreeInstances` | 小~中（∝树数） | 合并 + 真删（数组越用越小）+ 区域去重 |
| 树碰撞体重建（切 enabled） | **很大**（整张地形 + 全部树） | 合并/去重；根本解=关掉 Enable Tree Colliders 改"玩家附近独立 Collider 池"（`TreeDestructor` 已有 `_worldPos/_treeRadius/_treeHeight/_alive` 表可直接复用） |
| Detail 层清零（约 12 层 patch） | 小 | 合并 + 区域去重 |
| NavMesh `UpdateNavMesh` | **很大**（几百 ms~秒） | 长窗口/阈值/`NavMeshObstacle(carve)` 取代 |

优化方案（按性价比）：
1. **合并"生效点"**：`ModifyHeightMap` 拆成"写 patch"与"Sync 生效"，由 `TerrainClearer` 在一个处理点统一 `SyncHeightmap` + 树提交 + 碰撞体重建 + NavMesh，顺序对齐；一帧多坑只生效一次（视觉晚 1 帧可接受）
2. **区域去重**：`TerrainClearer` 维护"最近已清除圆"（中心+半径+时间，容量 ~32），新请求被旧圆完全覆盖（`dist+r ≤ R+ε` 且时间窗内）时**跳过 Tree/Rock/Detail 清除**（高度图照改）——炮击覆盖区反复炸时省掉最贵的两项
3. **三个独立节流**：树/草 0.1~0.25s、碰撞体 0.5s、NavMesh 1s+，且 NavMesh 加"上一次没烘完不发下一次"守卫；`RebuildTreeColliders` 只在"树/石真的被清或被改高度"时调（纯擦草不调）
4. **阈值化 NavMesh**：坑深/陡壁达阈值才标脏；终极用 `NavMeshObstacle(carve)` 表示弹坑，零重烘
5. 树实例改"真删"（代价：索引重排、失去 RestoreAll）

### 4.13 【定案】"跳不起来 + 打到看不见的墙" = 树冠碰撞体（半径 7.4m 的隐形巨胶囊）

## 【修复】天空层（星星/月亮/云）"吃雾就看不见、看得见就不吃雾"——已落地

需求：`Assets/Shader/Environment/SkyboxLayer.shader` 的远景天空层要同时"看得见 + 吃全屏雾"。

### 根因（两条独立的时序问题）
- 这些物体是包围相机的巨物（`Day-Night-Manager.prefab`：星星/云 cube scale 15000/13000、月亮 Quad z=-10000，相机远裁剪面 1000），全靠 shader 的 `ZClip Off` 才画得出来 → 顶点深度被钳到远平面，**与天空盒同一深度**
- ① 队列 <2500 → 走 URP 不透明 Pass(300)，随后**天空盒 Pass(400) 以相同深度整片重画**把它擦掉 → "吃雾但看不见"
- ② 队列 Transparent(3000+) → 在 450 的透明 Pass 画（天空盒 400 之后所以可见），但**全屏雾 Pass 注入点也是 450 且 Renderer Feature 同 event 排在 URP 内置 Pass 之前** → 雾先画、天空层后画盖在雾上 → "看得见但不吃雾"
- 佐证：项目内 `Assets/Scripts/Rendering/WarpingBeforeFogRendererFeature.cs` 的注释早已记录"雾 450 排在透明 Pass 之前"，并用 445 绘制绕过

### 落地实现
1. `SkyboxLayer.shader`：Pass 加 `Tags { "LightMode" = "SkyboxLayerBeforeFog" }`（Queue 仍留 Transparent，材质自定义队列 3000/3000/3500 决定互相顺序）
2. 新增 `Assets/Scripts/Rendering/SkyboxLayerBeforeFogRendererFeature.cs`：445（`BeforeRenderingTransparents - 5`）用自定义 ShaderTag 单独绘制；`FilteringSettings(RenderQueueRange.transparent)` + `SortingCriteria.CommonTransparent`
   - 关键：必须 `CoreUtils.SetRenderTarget(cmd, cameraColorTargetHandle, cameraDepthTargetHandle)` **同时绑深度**，否则丢掉 ZTest，云/星空会整片盖在地面上（Warping 那个 Pass 是 ZTest Off 所以只绑了颜色，不能照抄这一点）
3. 把该 Feature 注册进 `Assets/Setting/New Universal Render Pipeline Asset_Renderer.asset`（走 MCP `execute_code`：`SerializedObject` 取 `m_RendererFeatures` + `AssetDatabase.AddObjectToAsset` + 反射调 `ValidateRendererFeatures()` 自动重写 `m_RendererFeatureMap`）→ 现在共 5 个 Feature：Outline(300)/Snow(300)/WarpingBeforeFog(445)/FullScreenFog(450)/SkyboxLayerBeforeFog(445)
4. 验证：`refresh_unity`(force/all/compile=request) 后 `read_console` 0 error；`execute_code` 实测 `SkyboxLayer` shader `passCount=1 msgCount=0`、renderer `features=5` 且新 Feature `isActive=True`、3 个材质队列未变（3000/3000/3500）

### 副作用与替代方案
- ⚠ 自定义 LightMode 的代价：该 Feature 被禁用/移除后天空层**完全不显示**（没有默认 Pass 兜底），与 Warping 同一性质，已在 shader 与脚本注释里写明
- 备选方案（未采用）：把 fog 注入点从 450 改到 500（AfterTransparents）→ 零代码，但会让**所有透明物**都按不透明深度吃雾（前景粒子被远处地形距离误判），画面风险大
- 天空层在雾里得到的浓度与天空盒完全一致（它们的像素在雾读的深度纹理里同为远平面深度），所以不会出现天空与天空层色差

## 【修复】开局即夜晚时夜间照明战备不解锁（BattleManager 漏掉开局昼夜事件）
现象：`BattleManager.cs:478 OnDatSwitch` 在昼夜交替时 `Authorize(LampTowerId/IlluminatorId, !isNoon)`，但**开局初始就是夜晚时不生效**（夜间照明战备整夜锁着）。
根因定位（纯代码推导，无需编辑器）：
1. 玩法场景 `Assets/Scene/TestScene.unity` 里有 `Assets/Art/Prefabs/Day-Night-Manager.prefab` 实例（`DayNightBrain` + `DayNightTriggerModule` 等模块都在根物体上）；`DayNightTriggerModule.Initialize()`（`Effect/DayNightTriggerModule.cs:23-26`）在 `DayNightBrain.Start()` 里**无条件**抛一次 `GlobalEventSub.DaySwitch(IsNoon(state))` —— 这就是"开局那一次"。
2. 但 `BattleManager` 由 `ResSvc.AsyncLoadScene` 的回调创建，而 `ResSvc.cs:118-141` 明确把回调**延后一帧**（`DelayedInvoke`，注释写着"让场景中所有 Awake/Start 先完成"），且用 `LoadSceneMode.Single`。
3. ⇒ 场景内 `DayNightBrain.Start` 一定早于 `new GameObject("BattleManager").AddComponent<BattleManager>()`，`Awake` 里的 `GlobalEventSub.OnDaySwitch += OnDatSwitch` **永远收不到开局那一次**；之后 `DayNightTriggerModule.Tick` 只在状态翻转时才抛事件 → 开局是夜晚就整夜不抛。开局是白天看不出问题（本来就该锁着：`AirdropData.authorizeCounter` 默认 0 = "隐藏和无法使用"，见 `AirdropController.cs:418-421`）。
4. 顺带发现隐藏炸弹：即使事件收到了，`OnDatSwitch` 里用的 `ADCont` 是 `Init()` 协程里才创建的，早于它的调用会 NRE。
修复（2 个文件，编译 0 error）：
- `01Manager/Global/GlobalEventSub.cs`：`DaySwitch(bool)` 里先 `LastDaySwitchIsNoon = isNoon`（新增 `public static bool? LastDaySwitchIsNoon { get; private set; }`，null=本次运行还没产生过昼夜事件），再 `OnDaySwitch?.Invoke`。事件总线记住最后值 → 晚订阅者可补。
- `01Manager/Battle/BattleManager.cs`：`OnDatSwitch` 开头加 `if (ADCont == null) return;`；新增 `ApplyInitDaySwitch()`（读 `GlobalEventSub.LastDaySwitchIsNoon`，有值就调 `OnDatSwitch`）；在 `Init()` 与 `InitSpecial()` 两条路径的 `ADCont.Init(); CacheReinforceAd(); ADCont.transform.SetParent(transform);` 之后各调一次。
- 为什么不是"把订阅提前"：BattleManager 是运行时创建的，没有比"补发"更早的契机；也不是"把 ADCont 提前创建"（它还依赖任务/地形初始化）。
- 可复用的规律（已写进 MEMORY）：**凡是"场景物体 Start 里只抛一次"的初始事件，被 `AsyncLoadScene` 回调创建的模块必然漏掉，必须靠"事件总线缓存最后值 + 初始化后补发"**。同理注意 `NightLight`（Effect）在 `Awake` 订阅、场景物体，早于 `Start` 所以没问题。旧 `Effect/DayNightCycle.cs` 已不参与玩法场景。

### 【修复·续】上面的"补发"会把白天授权减成 -1 → 战备永久锁死（用户发现，已改）
用户问："初始授权是 0，如果对战初始是白天会不会被变成 -1 导致永远不能使用" —— **成立，是上面那版补发引入的回归**。证据：
- `ADSO_Y_Lamp.asset`：`ID: 16`（`LampTowerId`）+ **`authorize: 1`**；`ADSO_Y_Llluminator.asset`：`ID: 17` 同样 ⇒ `AirdropData.IsAuthorize => !cfg.authorize || authorizeCounter > 0`（`AirdropController.cs:451`），必须 >0。
- `AirdropController._Authorize`：`data.authorizeCounter += state ? 1 : -1;`（`:295`）**裸计数、无下限、无夹取**，全仓只有 BattleManager 这两行会动它。
⇒ 开局白天：`ApplyInitDaySwitch()` → `Authorize(id, false)` → `0 → -1`；入夜 `+1` 只回到 `0` ⇒ 探照灯/照明弹**整局永久锁死**。改造前之所以没暴露：开局事件被丢掉、白天什么都没做，恰好等于计数 0（"cancelled bug 救了它"）。
修复（只改 `BattleManager.cs`，编译 0 error）：把"白天"当作计数的**自然状态**，白天永不做减法：
- 新增字段 `bool? _dayIsNoon`（最近昼夜状态）与 `bool _nightAuthorized`（是否已按夜晚加过授权 = 去重标志）。
- `OnDatSwitch(isNoon)` 只做 `_dayIsNoon = isNoon; ApplyDaySwitch();`（不再直接 Authorize）。
- `ApplyInitDaySwitch()` 读 `GlobalEventSub.LastDaySwitchIsNoon` 填 `_dayIsNoon` 后调 `ApplyDaySwitch()`（无缓存值就用事件里存的那个）。
- `ApplyDaySwitch()`：`if (ADCont == null || !_dayIsNoon.HasValue) return; bool isNight = !_dayIsNoon.Value; if (isNight == _nightAuthorized) return; _nightAuthorized = isNight; Authorize(LampTowerId, isNight); Authorize(IlluminatorId, isNight);`
  → 开局白天：isNight=false == `_nightAuthorized`(false) ⇒ **什么也不做**，计数保持 0 ✓；开局夜晚：+1 ✓；之后每次翻转交替 +1/-1，始终落在 {0,1} ✓。
- ⚠ 一般化教训（已写进 MEMORY）：**"补发初始状态"遇到"计数制授权"时，必须只补"与自然状态不同的那一侧"，否则会把默认值减到负数**。
