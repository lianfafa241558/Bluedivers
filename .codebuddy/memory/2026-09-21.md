## 【诊断】"子弹和人都能穿过树、别处却有空气墙"——MCP 实测结论

用 Unity MCP（实例 `Bluedivers@4a3e6a7b`，port 6400，projectRoot 已核对）在 Play 模式下读了真实状态：

### 1. 树穿模的根因：树的碰撞体压根没生成
- `TerrainCollider.m_EnableTreeColliders = 0`（**Enable Tree Colliders 没勾**）→ 地形树碰撞体是"运行时由 TerrainCollider 按 TreePrototype 复制生成"的，开关关着就一个都没有 → 在树原型预制体上加的 CapsuleCollider **完全无效**，子弹/玩家都穿
- Terrain 对象：`Terrain`，layer=3(Ground)，`preserveTreePrototypeLayers=False`（=树实例会被强制改成 Terrain 的层 Ground），`treeInstances=374`，`treePrototypes=11`
- 实例分布：`[0]=37 [1]=36 [2]=43 [3]=50 [4]=42 [5]=41 [6]=37 [7]=22 [8]=22 [9]=25 [10]=19` → 与"0-6 石块 / 7-10 树"完全吻合（石块 286 + 树 88）

### 2. 运行时层掩码（GameContract.LayerDefinition @ 01_GameContract）
| 属性 | 值 | 层 |
| --- | --- | --- |
| HittableLayers（子弹） | 73 | Default + Ground + Unit |
| HittableHighSpeedLayers | 601 | + Water + OnlyProjectile |
| MoveableLayers（玩家移动） | 8265 | Default + Ground + Unit + **AirWall** |
| UnitSeeLayers | 16393 | Default + Ground + Smoke |
| GroundLayers / UnitLayers / AirWallLayers | 9 / 64 / 8192 | Default+Ground / Unit / AirWall |

→ 结论：Terrain 在 Ground 层、树实例也会落到 Ground 层，**只要开启 Enable Tree Colliders，子弹和玩家就都会正确撞树**，无需改 LayerConfigInitializer。
另外 `Physics.queriesHitTriggers = True` → 武器射线默认**会命中 Trigger**，而可命中层含 Default，容易被误判为"子弹打在空气上"。

## 【修复】天空层（星星/月亮/云）"吃雾就看不见、看得见就不吃雾"——已落地

需求：`Assets/Shader/Environment/SkyboxLayer.shader` 的远景天空层要同时"看得见 + 吃全屏雾"。

### 根因（两条独立的时序问题）
- 这些物体是包围相机的巨物（`Day-Night-Manager.prefab`：星星/云 cube scale 15000/13000、月亮 Quad z=-10000，相机远裁剪面 1000），全靠 shader 的 `ZClip Off` 才画得出来 → 顶点深度被钳到远平面，**与天空盒同一深度**
- ① 队列 <2500 → 走 URP 不透明 Pass(300)，随后**天空盒 Pass(400) 以相同深度整片重画**把它擦掉 → "吃雾但看不见"
- ② 队列 Transparent(3000+) → 在 450 的透明 Pass 画（天空盒 400 之后所以可见），但**全屏雾 Pass 注入点也是 450 且 Renderer Feature 同 event 排在 URP 内置 Pass 之前** → 雾先画、天空层后画盖在雾上 → "看得见但不吃雾"
- 佐证：项目内 `Assets/Scripts/Rendering/WarpingBeforeFogRendererFeature.cs` 的注释早已记录"雾 450 排在透明 Pass 之前"，并用 445 绘制绕过

### 落地实现
1. `SkyboxLayer.shader`：Pass 加 `Tags { "LightMode" = "SkyboxLayerBeforeFog" }`（Queue 仍留 Transparent，材质自定义队列 3000/3000/3500 决定互相顺序）
2. 新增 `Assets/Scripts/Rendering/SkyboxLayerBeforeFogRendererFeature.cs`：445（`BeforeRenderingTransparents - 5`）用自定义 ShaderTag 单独绘制；`FilteringSettings(RenderQueueRange.transparent)` + `SortingCriteria.CommonTransparent`
   - 关键：必须 `CoreUtils.SetRenderTarget(cmd, cameraColorTargetHandle, cameraDepthTargetHandle)` **同时绑深度**，否则丢掉 ZTest，云/星空会整片盖在地面上（Warping 那个 Pass 是 ZTest Off 所以只绑了颜色，不能照抄这一点）
3. 把该 Feature 注册进 `Assets/Setting/New Universal Render Pipeline Asset_Renderer.asset`（走 MCP `execute_code`：`SerializedObject` 取 `m_RendererFeatures` + `AssetDatabase.AddObjectToAsset` + 反射调 `ValidateRendererFeatures()` 自动重写 `m_RendererFeatureMap`）→ 现在共 5 个 Feature：Outline(300)/Snow(300)/WarpingBeforeFog(445)/FullScreenFog(450)/SkyboxLayerBeforeFog(445)
4. 验证：`refresh_unity`(force/all/compile=request) 后 `read_console` 0 error；`execute_code` 实测 `SkyboxLayer` shader `passCount=1 msgCount=0`、renderer `features=5` 且新 Feature `isActive=True`、3 个材质队列未变（3000/3000/3500）

### 副作用与替代方案
- ⚠ 自定义 LightMode 的代价：该 Feature 被禁用/移除后天空层**完全不显示**（没有默认 Pass 兜底），与 Warping 同一性质，已在 shader 与脚本注释里写明
- 备选方案（未采用）：把 fog 注入点从 450 改到 500（AfterTransparents）→ 零代码，但会让**所有透明物**都按不透明深度吃雾（前景粒子被远处地形距离误判），画面风险大
- 天空层在雾里得到的浓度与天空盒完全一致（它们的像素在雾读的深度纹理里同为远平面深度），所以不会出现天空与天空层色差

## 【调研】`Art/Nature/Rocks` 怎么加进场景（地形树 vs 场景预制体）——MCP 实测

用户问"想让 Rocks/Prefabs 下的物体加进场景增加地形起伏，该做成 Terrain 树还是直接放预制体"。用 MCP（`Bluedivers@3d9f2357`，已核对 projectRoot=E:/Bluedivers）实测，编辑态 TestScene：

- **Tree Prototypes 共 11 个**：`[0]-[6]` = `Art/Nature/Rocks/Lod/` 的 `Rock1LOD_grup1/2/3`、`RockLod1C`、`RockLOD1E`、`RockLOD4B`、`RockLOD6C`（都带 LODGroup，bounds 1.6~3.8m；除 grup3 外都带 Box/Sphere Collider）→ **同一个 rocks 包的地形树方案已经在用了**；`[7]-[10]` = Pure Poly 的 `PP_Birch_Tree_05 2`/`_06 4`/`PP_Tree_02 4`/`PP_Tree_10 2`
- `Rocks/Prefabs/`（12 个）是**无 LODGroup 的重版**，全仓只被 `Assets/Scene/TestScene.unity` 手摆过（无 prefab/场景引用）；巨石 bounds：`Rock5A` 34.6×28.5×25.2、`Rock2` 18.9×20.9×17.7、`Rock6A` 10.9×4.9×10.8、`Rock1A` 10.8×9.4×12.4（均**非凸 MeshCollider**），其余 2~5m
- 地形尺寸是**运行时**按 `taskCfg` 定的（`BattleManager.InitTerrain` 改 resolution/size：MapRes 512/1024、size=MapSize）→ **场景里预摆的 prefab Y 每局失效**，必须运行时 `TerrainUtils.WSToHeight(x,z)` 采样贴地
- `SpawnVegetation` 只设 position/width/height/prototypeIndex，**没设 `tree.rotation`/`tree.color`** → 撒出来的石头朝向全一致；`TreeInstance.rotation` 在 2022.3 文档里是正常字段（X-Z 弧度，只读=得自己构造结构体写）
- `probability` 实为**每格（高度图索引）**概率，格边长 = MapSize/mapRes（512/512 = 1m）
- **NavMeshSurface 实测**：MapRoot 上唯一一个，`collectObjects=Volume(1)`、`m_UseGeometry=0`(RenderMeshes)、`LayerMask=8`(Ground)；石块/树都在 **Default 层** → **都不进 NavMesh** → "石头当地形树 + Collider 生效"的结果是**玩家被挡、AI 直接穿过去**（AI 只认 NavMesh）
- `m_EnableTreeColliders`：场景 YAML 里 Teach/PV/TestScene = **1**（GameRoot/Utnapishitim/Test/GameEnd 无 TerrainCollider）——与本文件前面 Play 实测的 0 冲突，说明这开关被人改过，**动之前先核当前值**
- 联动坑：新增石块原型后，`ModifyTerrain.clearVegetationRange`（默认 (7,10)）不会清它们（弹坑只清树），`_destructibleTreePrototypes`（空=全可毁）与 `TreeDestructor.ClearInRadius` 的区间也要同步
- 落位插入点：`ApplyFractalNoiseToTerrain` 里 660-710 行之间（高度图提交之后、NavMesh 构建之前）

结论：小碎石→继续用地形树（现成 0-6，调 `rockSpawn` 概率 / 加 `rotation` 随机）；大岩体（要挡人/挡枪/可站/要独立朝向位置）→ 预制体 + 运行时贴地 + 放 Ground 层或挂 `NavMeshObstacle` 才能真正挡 AI。

## 【决策待定】"按地形类型放置石块（地形覆盖）"放哪：A=GenerateNoiseTerrain / B=MissionController
- **A 的时序优势（关键）**：`ApplyFractalNoiseToTerrain` 内部 = 高度图→alphamap→`SpawnVegetation`(石/树)→`SetTreeInstances`→`Rebuild`(TreeDestructor/TerrainDetailEraser)→`SpawnDetails`(草)→**NavMesh(686-709)**。所以"树/草之后、NavMesh 之前"这个位置天然存在 → 能① 直接在本地 `trees` 列表里剔除被覆盖实例（零提交、无过渡帧，不用走 `TreeDestructor` 的入队+4/s 限流）② 让 `SpawnDetails` 跳过覆盖圆（不用事后擦）③ 石头放 Ground 层能被**同一次** NavMesh 烘焙带走
- **B 的优势**：`MissionController` 有 `missionCreatPoints`（`List<(Vector2 Pos,int Range)>`）、`GenerateNewMissionPoint`（挑最平坦点）、`IsOverlapWithExistingPoints` → 占地避让现成；且 `InitializeAsync` 末尾 `TerrainUtils.AsyncRefresh(true)`（`MissionController.cs:80`）会 `nav.UpdateNavMesh` → 也能把石头带进 NavMesh
- **B 的硬伤**：① `_initMode == FindFromScene` 分支（`MissionController.cs:64-68`）没有 `missionCreatPoints`、也不走 AsyncRefresh → 避让逻辑静默失效 ② 此时树/草已提交，擦除只能走 `TreeDestructor.ClearInRadius`/`TerrainDetailEraser.ClearInRadius` 的入队限流（4/s、8/s）→ 跨帧、"石头下还立着树"的过渡帧 ③ MissionController 已很长，职责污染
- **依赖方向**：`08_Map.asmdef`(`FpsGame.MapUtils`, autoReferenced) 是低层、MissionController 在 Assembly-CSharp（上层）→ B 可随意调 A 的 API，反过来 A 引任务数据会破坏依赖方向 → **A 只能吃"地形维度"的数据（这正解释了"按地形类型枚举"天然属于 A）**
- 数据归属：`TerrainPresetData` 是 `GetTerrainPreset` 里代码内建的 **struct（非资产）**；挂 `GenerateNoiseTerrain` 的是场景 MapRoot → 检视器 list 属于**场景资产**（换地图要手改场景）。要"随地图/任务类型走"应上 SO（02Data、`_SO` 后缀），`taskCfg.terrainType` 来自 `mapItemInfos[u].terrainType`（`TaskManager.cs:146`）
- 倾向结论（待用户拍板）：**A 负责"撒"（地形规则 + 擦树擦草 + 随 NavMesh 一起烘），B 负责"让"**（A 把已放石头的圆/半径暴露成只读静态表，B 在 `GenerateNewMissionPoint` 里多一条判据）

## 【定案方向】石头=巨型悬崖（需可寻路），放 `GenerateNoiseTerrain` 的列表 + 概率进 `TerrainPresetData`
用户拍板：不用 SO（只有一个消费者/场景级），在 `GenerateNoiseTerrain` 上加 `List<{prefab, weight, footprintRadius}>`，`TerrainPresetData` 里只放生成参数。评估要点（我的补充意见）：
- **巨型悬崖不能用"每格概率"**：`SpawnVegetation` 是 heightmapRes² 逐格掷骰（适合 1~4m 小石）；要在 preset 里换成"目标数量/尝试次数 + 最小间距(半径倍数) + 圆互斥 + 坡度/高度过滤"
- **三条硬约束**：① 实例必须在 `SetTreeInstances` **之前**放（可直接从本地 `trees` 列表剔除覆盖处的树，零提交无过渡帧），并把覆盖圆传给 `SpawnDetails` 当排除区 ② 石头必须放 **Ground 层**（NavMeshSurface `layerMask=8` + `useGeometry=RenderMeshes`）才能被同一次烘焙带走 ③ 放完紧接着就是 NavMesh 烘焙（686-709），不需要额外 refresh
- **NavMesh 实测参数**（`ProjectSettings/NavMeshAreas.asset`，surface `m_AgentTypeID=-334000983`）：agentRadius 0.6 / agentHeight 2 / **agentSlope 60** / **agentClimb 1.5** / minRegionArea 2㎡；surface `m_VoxelSize=0.2` `m_TileSize=128` `m_MinRegionArea=2` `m_BuildHeightMesh=0` `m_IgnogreNavMeshAgent/Obstacle=1`。→ 悬崖坡面 >60° 自动成墙、顶面 ≥2㎡ 才可行走面
- 还需补的落点参数：垂直下沉 `sinkDepth`（否则坡地悬空）、随机 Y 旋转、避开 `GenerateNoiseTerrain.StartPoint` 与地图边缘、互相不重叠
- 风险：悬崖会切断 NavMesh 连通性 → 可能把任务点/巢穴/撤离点封在外面；可选护栏=烘完用 `NavMesh.CalculatePath` 抽检 StartPoint↔地图中心
- 层迁移无副作用：`LayerConfigInitializer` 里 `GroundLayers` 本身就含 Default+Ground（`HittableLayers=groundLayers|unitLayers`）→ Default→Ground 不影响"可击中/可移动"判定
