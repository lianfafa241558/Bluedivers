## `terrainData.heightmapResolution` 翻倍的代价（实测）
用户问："我把 terrainData.heightmapResolution ×2 对性能有很大影响吗"。
来源确认：`BattleManager.InitTerrain`（`01Manager/Battle/BattleManager.cs:208-217`）`mapRes = SizeType.Large ? 1024 : 512` → `heightmapResolution = mapRes + 1`（1025）、`alphamapResolution = mapRes`（1024）
⇒ **当前 `heightmapResolution-1 == alphamapResolution` 1:1**（这是下面那条单位 bug 一直没暴露的原因）。

MCP 实测（临时 TerrainData，`size=(640,96,640)`，同世界半径 20m 的 patch，8 次取平均）：

| heightmapResolution | TerrainData 内存 | 整张高度图初始化 + Sync | 20m patch | patch 格数 | GetHeights | SetHeights+SyncHeightmap |
|---|---|---|---|---|---|---|
| 1025（网格 1024²） | 2.1 MB | 417 ms | 64×64 | 4,096 | 0.02 ms | **5.96 ms** |
| 2049（网格 2048²） | 8.3 MB | **4631 ms（×11）** | 128×128 | 16,384（×4） | 0.04 ms | **23.63 ms（×4）** |

结论：
- **内存 ×4**（N² 线性）；**每个弹坑 / 每个 `ModifyTerrain` 条目的"写 + SyncHeightmap" ×4**（≈6ms → ≈24ms，爆炸时会明显掉帧）。
- **整张高度图写入 + Sync 是 ×11（超线性）** —— 这一步直接加在**开局生成地形**上（`GenerateNoiseTerrain` 是分块提交高度图，与我这次测的写入口径相同），是翻倍最痛的地方。
- 同量级增长的还有：`Terrain.Flush()`（实测 0.69ms @1025，O(N²)）、`UpdateNavMesh`（实测 5.6~8.8ms，体素化受分辨率影响）、TerrainCollider 的三角形数（物理查询/内存）、`RebuildTreeColliders`（它重建的是整个地形碰撞体）。
- **不受影响**：树实例、细节（草）层（各自独立分辨率：`detailResolution=512`）、地形渲染的 draw call（顶点自适应 LOD）、以及地形形状 —— `GenerateNoiseTerrain.mapscale = heightmapResolution / size.x` 只用在 `TerrainPosToWorldPos`，所有换算都按分辨率自适应，噪声频率不变。

## 顺手修的单位 bug：`ModifyAlphaMap` 必须用 `WRToAR`
`ModifyAlphaMap` 原来用 `WRToHR(outerHalfSize.x)` 求半径，再交给按 **`alphamapResolution`** 取 patch 的 `GetAlphas` —— 只因本项目 `heightmapResolution-1(1024) == alphamapResolution(1024)` 才恰好正确。**只翻倍 `heightmapResolution` 而不动 alphamap，贴图改动范围会跟着错 2 倍**（几何挖了、贴图没跟上）。
- 改动：`radiusRes` / `radiusZRes` 改用 `WRToAR(...)`（`Assets/Scripts/00Tools/Test/TerrainMainUtils.cs` 的 `ModifyAlphaMap` 开头，含说明注释）。
- **数值上是零变化**（今天 `WRToHR(l) == WRToAR(l) == FloorToInt(l/640*1024)`），`validate_script` 0 诊断、Console 0 error。
