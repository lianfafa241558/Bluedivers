## 咨询：UTF-8 vs UTF-8(BOM)（2026-10-02）

- 讲解口径：字节差异只有开头 3 字节 `EF BB BF`；实质差别是**读取方能否确定编码**（无 BOM 时 Windows 工具按 ANSI=GBK 猜 ⇒ 中文乱码 ⇒ 猜错后回存 = `U+FFFD` 不可逆损坏）；BOM 的代价是少数解析器把它当内容（sh 首行、JSON、正则 `^`）。
- 实测（写进 `topics/tooling.md`「编码基线 · BOM」）：`.cs` BOM 516 / 无 BOM 256 且全部合法 UTF-8（Roslyn 回退规则 ⇒ 不影响编译）；`.unity/.prefab/.meta` 带 BOM = 0（正确）；`TaskManager.cs` 内 **24 个 U+FFFD**（已损坏）；**9 个 `.shader` 是 GBK 编码**；`.editorconfig` 缺 `charset` 是无 BOM 的根因。
- 给用户的建议：`.editorconfig` 加 `[*.cs] charset = utf-8-bom`（+ 可选一次性补 256 个无 BOM 的 `.cs`，但会产生 diff）；Unity 资产/JSON 永不加 BOM；我编辑时保持文件现状。**未执行任何改动**（等拍板）。
- 用户追问「加 charset 会不会让之后新建文件默认带 BOM」⇒ 答复：**是，但仅限 IDE 保存路径**（新建 + 已有文件下次保存），管不到 Unity/脚本/PowerShell 写的文件；必须写在 `[*.cs]` 而不是 `[*]`（否则 VS 保存 `.json/.md` 也带 BOM）。此作用边界已记进 `topics/tooling.md`；仍未改动 `.editorconfig`。
- **用户「执行吧」⇒ 已落码**：`.editorconfig` 末段 `[*.{cs,vb}]` 追加 `charset = utf-8-bom`（用 `replace_in_file` 直改，锚点取末 3 行、唯一；**未写 `[*]`**）。验证：文件仍 无 BOM、**纯 CRLF 238/238**、新行插在最后且保持"末行无换行"风格、`charset` 仅 1 处。**未做**：256 个无 BOM 的 `.cs` 批量回填（打开+保存即自然收敛，或跑脚本）。
