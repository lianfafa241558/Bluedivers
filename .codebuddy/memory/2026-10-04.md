## 逻辑帧驱动重构（NetManager.Update）· 修「战备投弹 2.68s 漂到 3s」

- 起因：用户报"武器挂在鹰上，2.8s 到点、冷却 2.8s 后开火，有时 3s 才投弹"。排查结论：Jet(`deliveryType=2`) 分支里两条时间线互不校准 ——
  - ①「鹰到点」由 `PhoenixEagleController.UpdateDivingMovement` 用 `Time.deltaTime` 推：`Distance(startPoint,targetA)=√(650²+255²)=698.3`、`diveSpeed=250` ⇒ **≈2.79s**；且 Jet 分支**从不调** `SetDiveDuration`，与 SO 的 `arriveTime` 无关（`ADSO_RF_AirStrike` 里 `arriveTime:3` 是摆设）。
  - ②「投弹」由武器自身逻辑帧冷却：`Eagle Airstrike.prefab` 的 `_fakeAttrs Key4`(= `WeaponAttrType.StartCool`) `=2.68` ⇒ `WeaponReloadController.LogicInit` 里 `ShootInterval.CurrValue -= StartCool`，之后每 `LogicTick` `+= TickTime(0.02)`。
- 根因：`09Manager/Global/NetManager.cs` 旧 `Update` = **绝对 `Time.time` 比较 + 每渲染帧最多 1 tick** ⇒ **FPS<50 时逻辑帧率 = FPS**（44fps → 44 帧/s = 0.88×），按 `TickTime` 累加的冷却/射速系统性变慢；且债务 `Time.time-lastTime` **单调累积**，帧率恢复后最多 1 tick/帧地"快进"回放（1s 卡顿 ≈ 要 5s 真实时间才还完）。⚠ 注意不是"没追帧"，是"追帧速率被卡在 1 帧/渲染帧"。
- 改动（用户选 **B 方案：债务保留不丢弃**）：
  - 删 `PEInt lastTime` 与 `using PEMaths;`；新增 `static readonly float StepSeconds = Constants.LoginFrame.RawFloat`、`const int MaxCatchUpTicks = 10`、`float _accumulator`；抽出 `TickOnce()`。
  - `Update` = `_accumulator += Time.deltaTime;` + `while(_accumulator>=StepSeconds && ticks<MaxCatchUpTicks) { _accumulator-=StepSeconds; TickOnce(); ++ticks; }`。⇒ 逻辑帧率恒 50Hz，与渲染帧率解耦。
  - 用 `Time.deltaTime` 而非 `unscaledDeltaTime`：与旧 `Time.time` **同域**（都随 `timeScale`），暂停/慢动作语义不变。
- 顺带修「遍历期间增删」：新增 `_ticking` + `_pendingAdd/_pendingRemove`；`Add/Remove` 在 tick 期间改为**入队**（同帧 Add/Remove 互相抵消，保持调用顺序语义），`TickOnce` 末尾 `FlushPending()` 统一应用 ⇒ 避免 `LogicTick` 内销毁触发 `OnDestroy→LogicFrame.Unregister→Remove` 改动 `list` 而漏跳被顶上来的元素（`IsActive()` 有判空，不崩但静默少跑）。
- 验证：`plans/offline_compile.py 09_Managers` = **0 错误**（仅两条既有 CS0649）；Unity 单文件 `ImportAsset(ForceUpdate)` 后**三证齐** —— `09_Managers.dll` mtime 前进到 `16:11:57` + Console 清空后 **0 error** + `is_compiling:false`；并用 `findstr` 在 dll 二进制里搜到 `TickOnce`/`MaxCatchUpTicks`（排除"假空转"）。
- ⚠ 环境变化：MCP 实例实时 hash 已变 —— **`Bluedivers@4a3e6a7b` / port 6401**（规则里写的 `3d9f2357`/6400 过期；`mcpforunity://instances` 当时只连了这一个）。
- 未做（待拍板）：① `PhoenixEagleController.OnHide()` 为空 ⇒ `_diveSpeedScale`/`_diveTargetDuration`/`waitTime` 不复位，池化复用时俯冲时长会漂；② `VFXAirdropEffect.EndJet` 用 `Tool.Destroy(m_creatObject.gameObject, 2)` 延迟销毁鹰的子物体（武器），而鹰走 `VFXManager.Creat` 池化 ⇒ 可能带旧武器复出；③ Jet 是否补 `SetDiveDuration(data.arriveTime)`，让 SO 的 `arriveTime` 真正参与投弹时序。

## UI「VerticalLayoutGroup 下子项重叠、隐藏再显示才正常」根因（Unity 实测）

- 现象：UI 已挂 VerticalLayoutGroup，改完 TMP 文本后子项仍重叠；`SetActive(false)`→`(true)` 后正常。截图对应 `InformationWnd`（红底橙金字信息条，模板文案"侦测发现折跃信号"）+ `NoticeWnd`（portrait/noiteName/desc）。
- **根因（关键）**：`LayoutRebuilder.ForceRebuildLayoutImmediate` **只跑 `CanvasUpdate.Layout` 阶段**，而 **TMP 的文本度量（preferredHeight）要到 `CanvasUpdate.PreRender`（Graphic rebuild）阶段才更新** ⇒ 同帧内刷布局读到的是**旧高度** ⇒ 按旧高度摆位 ⇒ 重叠。
  - `TMP.ForceMeshUpdate()` **实测也无效**（它重建 mesh，但不重置 TMP 的 layout 尺寸缓存）。
  - `SetActive(false)→(true)` 有效，因为 TMP `OnEnable → SetAllDirty` 会重算度量。**这就是"隐藏再显示才正常"的全部原因。**
- 实测数据（`NoticeWnd.prefab` 的 `Image` 容器 584x114，子项 Title 200x30 + Desc）：
  | 做法 | Desc.h | Image.h |
  |---|---|---|
  | 换长文本 + ForceRebuildLayoutImmediate | 22.6（旧）| 114 ❌ |
  | 同上，再刷一次 | 22.6 | 114 ❌ |
  | 换长文本 + TMP.ForceMeshUpdate() + 刷布局 | 22.6 | 114 ❌ |
  | 换长文本 + **Canvas.ForceUpdateCanvases()** + 刷布局 | **67.7** | **136.6** ✅ |
  | 隐藏→改文本→显示 | 67.7 | 136.6 ✅ |
- 附带实测（澄清一个常见误解）：父 VLG 会**完全忽略 `activeInHierarchy == false` 的子物体**（不占位）；子项 `SetActive(true)` + `Canvas.ForceUpdateCanvases()` 后位置**是正确重排**的（-50/-150）⇒ "SetActive 不触发父 VLG 重排"不成立，真凶是 TMP 度量滞后。
- 项目内同类踩坑点：`00Tools/WndRootTool.cs:174 RefreshLayoutImmediate`（只调 ForceRebuild）、`10UI/UI/Subtitle/SubTitleShout.cs:92-94`、`SubtitleNPC.cs:59-60`、`10UI/UI/MissionHUDItem.cs:58/98/103`（`RefreshContentSizeFitter` 被注释掉）、`SelectRoleWnd` 十余处 `RefreshLayout`。
- 解法（顺序不能反）：`Canvas.ForceUpdateCanvases(); LayoutRebuilder.ForceRebuildLayoutImmediate(rt);`
  - 建议在 `WndRootTool` 加 `RefreshLayoutAfterText(Transform)` 统一封装；⚠ `Canvas.ForceUpdateCanvases()` 是全局开销，只对"一次性改文本+要立刻对位"的场景用，逐帧打字机场景可省。
- 配置层面（独立于上面的时序问题）：`NoticeWnd` 的 `Image` 用 `ContentSizeFitter(VerticalFit = MinSize)`，而子项是 TMP、`minHeight` 恒为 0；且 VLG 的子物体上挂了 `ContentSizeFitter(Desc = PreferredSize)` —— **Unity 官方禁止在 LayoutGroup 子物体上挂 ContentSizeFitter**，与 `ChildControlHeight` 二选一。`NPCSubtitle.prefab` 的 `bg`（VLG ch=false + CSF PreferredSize，子项 desc 又挂 CSF）同病。

## 「NoticeWnd 与 InformationWnd 两窗口互相重叠」根因（2026-10-04 实测 Play 中的 TestScene）

- 用户澄清：不是子项重叠，是**两个 Window 互相重叠**。用户新建了容器 `/GameRoot/CanvasRoot/VecticalUI`（名字拼写 Vectical）+ VLG 想把 HUD 窗口竖排。
- 运行时实测结构：
  - `VecticalUI` 的 VLG：**ch=False, cw=False, exH=False, exW=False, sp=0, align=UpperCenter**（padding.top 反推 ≈100）；子物体顺序 [NoticeWnd, InformationWnd]。
  - `NoticeWnd` rect 648x200，anchor(0.5,1)~(0.5,1)，pivot(0.5,1)，**prefH=0 / minH=0**，根上只有 `Animator`（无 VLG/CSF/LE）。
  - `InformationWnd` rect 648x100，anchor(0,1)~(0,1)，pivot(0.5,0.5)，**prefH=44 / minH=44**，根上只有 VLG（无 CSF/LE）。
  - 排好后的正常态 worldY：NoticeWnd [780,980]、InformationWnd [680,780]（首尾相接，间距 0）。
  - ⚠ 场景里另有一个**游离** `NoticeWnd(Clone)`（`parent=null`、scene=TestScene、worldY 为负 ⇒ 屏幕外），疑似残留，待用户确认是否清理。
- 三条根因：
  1. 父 VLG **ch=False** ⇒ 不用 preferredHeight，只用子项**当时**的 `rect.height` 摆放；而窗口高度是 prefab 写死的 200/100。
  2. 两个窗口的 **anchor/pivot 各不相同**（(0.5,1)/1 vs (0,1)/0.5）⇒ 在 VLG 第一次接管前按各自 prefab 的绝对定位显示，必然错位/重叠；`Window.SetWndState` 只 SetActive，不通知布局。
  3. **父 VLG 完全忽略 `activeInHierarchy==false` 的子物体**（实测：两子项均 inactive 时 VLG 的 `preferredH=0`、不占位）；窗口 prefab 默认 inactive（`InformationWnd.prefab` 根 `m_IsActive: 0`）⇒ VLG 计算时"看不见"它们，`SetActive(true)` 那一帧才接管 ⇒ 没赶上的那一帧就是"重叠"；隐藏再显示 = 又强制走一遍 `OnEnable→SetAllDirty→rebuild` ⇒ 正常。**这就是"隐藏再显示才正常"的机制。**
- 两颗未爆的雷（一旦改配置就会炸）：
  - `NoticeWnd` 根 prefH/minH = **0**（无任何 ILayoutElement）⇒ 把父 VLG 勾上 **Child Control Height** 后它立刻塌成 0 高、与邻居完全重叠。
  - `InformationWnd` 根自带 VLG ⇒ 它的 prefH=44 = 当前信息条数×44，**不是窗口高度**；父 VLG 若采用它，窗口高度会随信息条数跳变。
- 排除嫌疑：`NoticeWnd` 的 Animator（controller `NoticeWnd`，clip `NoticeWnd_Enter` 0.33s）**只驱动 `m_LocalScale`**，不碰 anchoredPosition/sizeDelta，不是元凶。
- 修法：① **推荐「槽位」**：VLG(ch=true) 下放两个带 `LayoutElement(preferredHeight=200/100)` 的空节点，窗口 anchor 拉伸 (0,0)~(1,1) 铺满槽位；② 或**直接挂**：父 VLG 勾 ch=true + 两个窗口根各加 LayoutElement(200/100) + 统一 anchor(0,1)~(0,1)/pivot(0.5,1) + `SetWndState(true)` 后补 `MarkLayoutForRebuild(parent)`。待用户选 A/B 后再动手。

## CountDownWnd「高度有时为 0」根因（2026-10-04 实测，用户已按方案 B 改了 VecticalUI）

- 实测：`CanvasRoot/VecticalUI` VLG(**ch=True**, cw=False, sp=0, align=UpperCenter, pad=100/0)，children=[CountDownWnd, NoticeWnd(inactive), InformationWnd]
  - `CountDownWnd` rect 330x**0**，`LayoutElement(pri=1,minH=95,prefH=95)`，`ILayoutController=<none>`
  - `NoticeWnd`(inactive) `LayoutElement(pri=1,minH=0,prefH=160)`
  - `InformationWnd` rect 648x**44**（prefab 设计 100）：根上 `VerticalLayoutGroup(pri=0,minH=44,prefH=44)` + `LayoutElement(pri=1,minH=-1,prefH=-1)`
- **根因 = 属性争抢 + 改 sizeDelta 不触发重排**：
  - `CountDownWnd.cs` **3 处手动写 `sizeDelta.y`** 做展开/收起：`FirstShowWnd()`(L83-85 设 0)、`Stop()`(L137-138 设 0)、`ApplyValue()`(L174-175 `show ? height : 0`)
  - 父 VLG `ch=True` + `LayoutElement` 会让 VLG **也**写 `sizeDelta.y`(=95)
  - ⚠⚠ **手动改子物体 `sizeDelta` 不会让父 LayoutGroup 重排**（RectTransform 尺寸变化不触发 SetLayoutDirty 到父级）⇒ 代码设成 0 后就**停在 0**，直到下一次 VLG 重排（别的窗口开关/信息条增删）才被改回 95 ⇒ **"有时 0、有时 95"**
- 附带 3 个问题：
  1. `InformationWnd` 被压成 44 高：父 VLG 采用它根上 VLG 的 `prefH=44`(=信息条数×44)，其 LayoutElement 是 `-1/-1`(=没设)。**修：该 LayoutElement 填 Min/Preferred Height = 100**（pri=1 压过 VLG 的 pri=0）。
  2. `NoticeWnd` 的 LayoutElement `minH=0` 建议一并填成 160。
  3. ⚠ `FirstShowWnd()` 里 `height = (int)rect.rect.height` **采样时机错**：`SetWndState(true)→SetActive(true)` 同步调用它，此刻 VLG 尚未重排 ⇒ 若 prefab 初值为 0 则 `height=0`，倒计时**永远展开不了**。
- 建议修法（保留 VLG 管高度）：`CountDownWnd` 不再改 `sizeDelta`，改为改根上 `LayoutElement` 的 **`minHeight` + `preferredHeight` 一起**（只改 preferred 会被 min=95 顶住），并 `LayoutRebuilder.MarkLayoutForRebuild(transform.parent as RectTransform)`；`height` 改从 LayoutElement 初值/prefab 常量取。备选：父 VLG 取消 ch，但仍需在改高度后显式 MarkLayoutForRebuild。待用户确认后动手。

### 补充实测（2026-10-04 晚，三种「收起高度」做法对照）

- `VecticalUI` 的 VLG 实测：**childControlHeight=True、childScaleWidth=False、childScaleHeight=True**（用户全勾了）；padding.top=100。
- 各窗口实测：`CountDownWnd` Animator=False；`NoticeWnd` **Animator=True + localScale=(3, 0, 1)**（被 `NoticeWnd_Enter` 动画改过，动画曲线 = `<self>::m_LocalScale.x/y/z`）；`InformationWnd` Animator=False。
- **对照（cd 高度 95↔0，观察 `InformationWnd.anchoredPosition.y`：95→-195、0→-100，差 95）**：
  | 做法 | cd.rect.h | info.ay | 结论 |
  |---|---|---|---|
  | `ch=false` + `sizeDelta.y=0` + MarkRebuild | 0 | -100 | ✅ |
  | `ch=false` + `localScale.y=0` | **95** | -100 | ✅ 仍上移 —— **因为 `childScaleHeight=True` 让 scale 参与占位** |
  | `ch=true` + `sizeDelta.y=0` + MarkRebuild | **95** | -195 | ❌ **被 VLG 顶回 preferredHeight，完全无效** |
  | `ch=true` + `LayoutElement.minH/prefH=0` | 0 | -100 | ✅ |
- **结论**：用户想用 `localScale.y=0` 替代 `sizeDelta` **能工作**（依赖 `Child Scale Height`），但代价是**任何子窗口的 scale 动画都会影响布局** —— `NoticeWnd` 的 `NoticeWnd_Enter` 正在驱动 `m_LocalScale`，它弹出时会把 `InformationWnd` 逐帧往下顶（占位 0→160），可见抖动。**推荐改用 `LayoutElement.minHeight/preferredHeight`（0↔95）+ `MarkLayoutForRebuild(transform)`**，不碰 scale/sizeDelta；并可把 `Child Scale Height` 取消勾选。
- 用户口径：**`InformationWnd` 的「44 × 项数」是有意为之，不要改**（其 LayoutElement 保持 `-1/-1`，由根上 VLG 的 prefH 决定）。
