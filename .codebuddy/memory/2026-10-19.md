## 小地图铁轨线不显示：RailRoutes 上没有 CanvasRenderer

- 现象：Hierarchy 里 `RailRoutes` 存在但"什么子物体都没有"，小地图上没有任何线（用户截图确认）。
- 诊断（MCP `execute_code` 读运行中真实状态，Play 中）：`graphic`/`routes=2`/`project` 都在，`rect=(−256,−256,512,512)`，
  轨道点投影 `p0=(289.28,6.59)`、`pmid=(197.73,210.05)` 都在框内 ⇒ **几何数据没问题**；但 `go.GetComponents<Component>()`
  里没有 `CanvasRenderer`，读 `Graphic.depth` 直接抛 `MissingComponentException: There is no 'CanvasRenderer' attached`。
- 根因：`[RequireComponent]` 只在**编辑器 Add Component 菜单**生效，**运行时 `AddComponent` 不会自动补依赖**。
  `Graphic` 靠 `canvasRenderer.SetMesh(...)` 提交网格，没有它 ⇒ 一条顶点都画不出来（表现=空物体、画面无线）。
- 修法：`new GameObject("RailRoutes", typeof(RectTransform), typeof(CanvasRenderer))`（`MiniMapWnd.CreateRailGraphic`）。
- 顺带验证（编辑器内空跑，不依赖 Play）：建同样的 GO + 恒等投影喂 3 段折线，反射调 `OnPopulateMesh(VertexHelper)`
  → `verts=8`（2 段在框内、1 段出界被 Liang–Barsky 裁掉），首个四边形顶点 = 拐点 ±1.5px，符合预期。
  ⚠ 反射取 `OnPopulateMesh` 必须定点重载（`Graphic` 同时有 `VertexHelper` 和 `Mesh` 两个版本，直接 `GetMethod` 会 AmbiguousMatchException）。
- 结论：以后在**运行时**给 Graphic/Renderer 类组件建 GameObject，依赖组件（CanvasRenderer/MeshFilter/MeshRenderer/RectTransform）
  都要在 `new GameObject(name, typeof(...))` 里写全，别指望 RequireComponent。

## 小地图铁轨线：去掉"碎折角"——按弧长分桶取平均 + 虚线改成按长度

- 用户反馈：为了做软边把轨道拆得太碎，小地图上每 5~6px 一个折角（毛刺）；"完全可以变成一段一段的直线（取轨道的平均值）"。
- 数据：轨道点距 ≈6.5m（160 点/条），小地图 ≈0.875px/m（NowMapSize≈585m/512px）⇒ 折角间距只有 5~6px，所以看着碎。
- 改法（`MiniMapRailGraphic`）：
  1. `BuildStraightRoute()`：按**世界弧长**分桶（`simplifyStep=30m`），桶内所有点取平均作为该段代表点 ⇒ 一段段直线；末点强制用真实终点（否则轨道短一截）。
  2. 虚线不再按"折线段序号"算，改成**按弧长**铺：`dashLength=21m` / `gapLength=7m`（≈3:1），
     每个实线小段再投影+裁剪+生成四边形。这样改简化步长不会连带改变虚线节奏。
- 验证（编辑器空跑，反射调 `BuildStraightRoute`/`OnPopulateMesh`）：
  - 每点 ±3px 抖动的 60 段折线 → 简化为 22 段，**中间点偏离 0.00px**（抖动被平均干净）；
  - 480px 直线 → 实线总长 361px，占空比 0.752（期望 21/28 = 0.750）。
- 遗留注意：`OnPopulateMesh` 里的投影必须喂"锚点坐标（0..512）"，自测时传负坐标会被 `rect.min` 再推出去，看着像算法错。

## 小地图铁轨线 · Unity 卡死（无响应）事故与加固

- 现场：用户"进入游戏"时 Unity 无响应。`Editor-prev.log` **最后一条消息** = `警告任务Robbery(Clone)没有实体`
  （`MiniMapWnd.MissionPointCreat` ← `BattleEventBus.MissionStart` ← `MissionBase.EventStart`），即卡死点就在
  "小地图开始建线"那一帧附近；日志里**没有任何异常/刷屏**，Windows 事件日志也没有崩溃/挂起记录（手动杀的，无 dump）。
- 我写的风险代码（v2 版）：`OnPopulateMesh` 里用 `while (walked < len) { ... walked += piece; }` 铺虚线 ——
  **自增靠浮点累加**，一旦 `piece` 小于 `walked` 的精度就永远不前进 ⇒ 直接卡死编辑器。这类"用 float 累加当循环进度"
  的写法在 UI 重建里是致命的（每帧重建一次）。
- 修法：改成**按整数周期枚举**（`for (int k = firstCycle; k <= lastCycle; k++)`，区间 = `[k*cycle, k*cycle+dash] ∩ [start,end]`），
  迭代次数只由 `len/cycle` 决定，天然有界、不依赖累加进度。另加：`len` 非有限/退化跳过、`dash` 用 `Clamp(0.1, cycle)`、
  顶点硬上限 `MaxVerts=40000`。
- 可观测性/开关（下次卡住能定位）：`[小地图/铁轨] 开始生成网格：路线 N 条` + `... 简化后共 M 点 / 网格顶点 K`
  （每次 `SetRoutes` 只打一次）；`MiniMapWnd` 新增 `显示铁轨路线` 开关，关掉就不建对象、不进画线代码。
- 旁证：float32 语义仿真旧循环 20 万组参数（phase 0~1100 / len 0.01~40）**没复现**卡死；新代码压测 2×160 点、
  连续重建 200 次 = 35ms（单次 0.176ms、212 顶点）⇒ 顶点量不可能造成卡顿。所以"不能 100% 断言就是自增循环"，
  但那条循环无论如何都该改（形态上就是会挂的写法）。
- 教训：UI `OnPopulateMesh` 里**任何循环都必须有整数迭代界**（或明确的最大步数），不能靠"每次至少前进一点"的浮点假设。
