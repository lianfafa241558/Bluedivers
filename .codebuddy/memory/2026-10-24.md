## 修复 SnowflakeScreen_URP.shader 编译错误
- 报错：`undeclared identifier 'UnityGet2DClipping'` —— 该函数只在内置 `UnityUI.cginc` 里，URP `Core.hlsl` 不带 ⇒ URP UI shader 里不能直接调。

- 核验：MCP `refresh_unity` 后 Console 0 error（实例 hash 实时为 `Bluedivers@4a3e6a7b`，与 rules 里写的 3d9f2357 不同）。
- ⚠ 复发一次：用户外部编辑器里该文件有旧缓冲，保存时把我的改动覆盖回去（frag 又变回 `UnityGet2DClipping(IN.worldPosition.xy, _ClipRect)`，并新增了 `worldPosition : TEXCOORD2` 与世界坐标赋值），报错行号从 118 变成 134。⇒ 改这类「用户正在编辑器里开着的文件」前先提示其关闭/重载，或改完让其保存前别再改；再次修复时只需把 frag 裁剪段换回 ifdef + `IN.clipPos`，并删掉多余的 `worldPosition` varying。

## 探照塔「大范围爆炸不吃伤害」诊断（MCP 运行时实测，未改代码）
- 结论：不是爆炸半径/队伍/遮挡口径的问题，是 `Damageable.Health` 在**全场景**都是 null ⇒ `Damageable.InflictDamage` 第一行 `if (!Health.IsValidMono()) return;` 静默丢弃所有伤害（爆炸/直击/流血同一条路）。
- 实测：场景 `EntityRoot/Mission_DetectorTower(Clone)/BigTowerBase/DetectorTower`（Actor Type=Enemy/Team=2/rangeLength=6/HalfHeight=8，`MainDamageable=null`，`Damageables=[Detector]`）。`Detector` 上 Damageable：`Health=null`、`Actor=DetectorTower`（非空）、`m_colliders` 长度 1 ⇒ **Awake 跑完了，只有 Health 没赋上**。全场景 717 个 Damageable 中 716 个 Health=null（含所有敌人 HitBox）；手动反射重跑一次 `Damageable.Awake` 立刻变成 ok。
- 根因：`Damageable.cs:183-187` 用 `GetComponentInParent<IHealth>()`（**接口泛型**）在 Awake 时机拿不到父级 `HealthEnemy`，返回 null；同一方法块里 `GetComponentInParent<Actor>()`（具体类）成功 ⇒ 同父级、同时机的对照实验。`IHealth` 全项目只有抽象基类 `Health` 一个实现 ⇒ 改 `GetComponentInParent<Health>(true)` 即可（自身优先那次 `GetComponent<HealthEnemy>()` 也应放宽到 `Health`）。
- 第二阻断点（仅编辑器 Play）：`Health.cs:241` 的 `#if UNITY_EDITOR` 伤害数字 `Tool.DrawLabel` 抛 NRE（`DrawLabelUtils.TextInfos` 只在 `Start()` 初始化，`Tool` 静态构造里 `AddComponent` 的实例 Start 未跑），异常会**中断 TakeDamage、扣血语句没执行**。修法：`DrawLabelUtils` 的 `TextInfos/ShapeInfos` 改字段初始化器，别依赖 Start。
- 其它同场景事实（不是本次主因，修好 Health 后仍可能挡）：`BigTowerBase` 只有一个 8×19×8 `BoxCollider`（无 Damageable/Actor）⇒ 它只是壳，且在 `Damageable.ExplosionBlocking` 里当遮挡物（塔的 `Detector.isMain=false`，非内半径时要射线到 bounds.center，底座会挡）；`Actor.rangeLength=6` 参与 `UnitQueryGrid.QueryUnits` 的 `range.Overlaps(unit.Range)` 水平预筛。
- 复用工具：新增 `plans/prefab_components.py <prefab> [名字过滤]`，打印每个 GO 的 layer + 组件（含 MonoBehaviour 脚本名、Collider 尺寸/trigger），一眼看出"有没有 Collider/Damageable/Actor"。

## 同上续：GuardDog 是飞行单位 ⇒ 移动升级为三维（水平避障 + 垂直爬升）
- 关键事实：原实现 `toTarget.y = 0f` ⇒ **完全没有垂直速度**，所以"目标在楼顶"时它不会"在 y 上卡住"，而是**永远顶在大楼外墙上**（水平也被挡），楼顶目标根本拿不到。CC 也没有重力补偿（本来就不用）。
- 改法：`desired = toTarget/distance` 保留 Y；水平分量交给 `Steer`，垂直单独 `VerticalSpeed()`；`SmoothDamp` 合成三维速度（maxSpeed 放大到 1.5×speed）。
- `climbOver`：**目标在上方 0.5m 以上 + 前方探测被挡 + 头顶有净空** ⇒ 本帧水平速度清零，先原地升到目标高度再推进（否则会贴楼面横爬，被窗台/挑檐钩住）。⚠ 三个条件缺一不可：头顶没净空时若也停横向会**彻底死锁**。
- `HasHeadroom()`：胶囊向上 cast `radius + skin*2 + 0.25`，被楼板/天花板挡就拒绝抬升；`VerticalSpeed` 里"上升"一律先过这一关。
- 脱困顺序（`BeginDetour` 返回 bool）：上方有净空 → `_climbTimer`（直上，飞行单位最快）；否则 → `_detourTimer` 沿 `Cross(up, normal)` 侧移。
- `UpdateStuck` 改为 3D 位移统计（原来压平 Y 会把"原地爬升"误判成卡住）。
- `RotateToTarget` 改为忽略 Y（只水平转身）：爬升后目标在正下方，带 Y 的 LookRotation 会让机体俯冲翻转。⚠ 这会改变"上下坡时狗会俯仰看目标"的旧表现。
- 已知边界：狗在**封闭房间/头顶是楼板**的室内、或封闭天井里，steering 出不去（没有门的先验）⇒ 需要 NavMesh/门锚点，纯避障解决不了。
- 核验：`read_lints` 0 error + csc 单文件无 CS1xxx。
