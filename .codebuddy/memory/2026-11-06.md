## 武器评分类 · 真实伤害口径修正（两个真 bug）

用户拿 `Health.HandleDamage` 提问："直击 10 + 动能1 + 燃烧1 实际是 20 点"。核对结论：

1. **加法口径本来是对的**：`Damageable.InflictDamage` 里 `value = damage × 系数` 逐条入账，
   `HealthCoefficient` 也是**求和**（不是平摊）⇒ 10 × (1+1) = 20 ✓。
2. **Bug A：`CountsToHealth` 把 Freeze 判成"不掉血"**。`HandleDamage` 的 Freeze 分支是
   `AddOpposedAboGauge(...); return value;` —— 一边推积蓄槽一边照常掉血。
   旧注释（"Freeze 只加积蓄槽"）是过时口径 ⇒ 所有冰冻类武器的真实伤害被算成 0 或只剩动能那部分。
3. **Bug B：`RealDamageRatio` 被 `Clamp01` 压到 1**，多类型叠加（比值 >1）完全看不见：
   `RealDamageText` 用 `ratio < 0.999` 判断 ⇒ "10→20" 永远不显示，看起来像真实伤害没算。
   改成不 clamp，判断改 `Mathf.Abs(ratio - 1) > 0.001`，明细提示分"<1 混了削甲/推槽成分"与
   ">1 多类型各结算一次"两种文案。
4. 实测（修完）：水球埴轮 面板单发 61 → 实际 **464**（落地特效 `Vfx_SmokeIce` 的持续组是
   **[Gun:1, Freeze:13]** ⇒ 每拍 1×(1+13)=14 点、31 拍 = 434，加爆炸 30），总分 27.8→**53.4**；
   骑行水壶 66→469（同样 7.1 倍）；闪光弹/油漆桶 仍是 0（只有 Vertigo/Destruction，本来就不掉血）。
   ⚠ 这类"系数和 >1"是数据决定的（引擎里每个条目各结算一次），不是评分放大 ——
   若觉得伤害离谱，要回去看 `DamageGroupDirect/Explosion` 的配置，别在评分里除回去。

## 武器评分类 · 热量武器的节奏择优（打满过热 vs 停火散热）

- 新口径：热量武器不再一律按"打满过热 + 锁 OverheatDuration"算节奏，而是两条路线比吞吐：
  - **A 过热流**：`rateA = n / (n×Interval + OverheatDuration)`，n = `BurstShots`；
  - **B 散热流**：打 `n-1` 发就停手，`ventPause = CoolDelay + (n-1)×EffectiveHeat / CoolSpeed`，
    `rateB = (n-1) / ((n-1)×Interval + ventPause)`（稳态：每轮散掉自己攒的那些热）。
  - `rateB > rateA` ⇒ 用 B，否则保持 A。n-1 < 1（一发就过热）时只能走 A。
- 落地：新增 `report.HeatCycleShots / HeatCyclePause / HeatStyleVent / CoolDelay`；
  `dumpTime` 里把 `BurstShots/OverheatDuration` 换成 `HeatCycleShots/HeatCyclePause`
  ⇒ `SustainedDps`（有效 DPS）与 `ClearRate`（清杂）都自动跟着走；`MagazineDamage` 仍按理论过热发数（描述热量上限）。
- 实测（BeamRifle/光之剑超新星，CoolSpeed 110/s、CoolDelay 0.3s、每发 4.5 热、Interval 0.0596）：
  过热 23 发（rateA 5.94/s）vs 打 22 发 + 停 1.2s（rateB **8.77/s**）⇒ 取 B，ClearRate 5.34→8.77、DumpTime 750 发 85.5s；
  科莱特微波枪 12→11 发（停 1.2s vs 锁 3s）同样取 B；

### 穿透/爆炸不进清杂的两个洞

1. **Special（「贯穿弹头」= Special 穿透单位 +1）被丢掉**：`AppendMods` 之前直接 `continue` 跳过 Special，

   实测阿波罗装「连锁爆弹」：直击 21→5、爆炸 0→10、半径 0→4、多目标 ×1→**×6**、清杂 15.97→**50.19** 只（清杂分 100）、总分 22.6→**34.8**。

- UI 新增一行"爆炸范围：半径 X m 按面积估约罩住 N 个杂兵（伤害 A→B）；只计入清杂"。

### 尾迹的 5 秒持续伤害要在清杂里按时间轴折算（否则清杂恒 0）

- 用户质疑："尾迹持续 5 秒一直造成伤害，为什么计入 0 分？"
- 真相：尾迹**有**计入（单发 150→194 = 11 拍 × 4），但清杂的 0 分来自另一处：
  44 点被整体塞进"每次扣扳机"，而书记的惩戒 10 秒只能扣 1.45 次（Interval 5s 蓄力 + 每次消耗 60 弹）
  ⇒ 4.02 只 < 清杂锚点下限 5 只 ⇒ 0 分。
- 修法（`_ScoreCompute.cs` 清杂段）：把尾迹从"每次扣扳机"里**拆出来按时间轴算**：
  - `trailDamage = DerivativeRealDamage × ArmorFactor(1甲, AP)`，`shootDamage = clearArmorDamage - trailDamage`；
  - `trailSeconds = min(10s, 扣扳机次数 × DerivativeDuration)`（一条尾迹活 5s，且不超过窗口）；
  - `TrailKills = trailDamage / Duration × trailSeconds × 多目标 ÷ 50`；
  - `ClearKillsIn10s = 扣扳机击杀 + TrailKills`。
  新增 `report.TrailKills` / `DerivativeRealDamage`；清杂行显示 `…·尾迹3.5`。
- 实测：书记的惩戒 TrailKills **3.54**、清杂击杀 4.02→**7.57 只**、清杂分 0→**7.3**、总分 31.0→**32.5**。
- ⚠ 只对 `TrailsUnits` 生效（跟着子弹飞的尾迹）；燃烧弹/水球那类"落点固定"的持续效果仍按原口径（并入单发），要一起改再说。

## 伤害 · 范围/爆炸的元素成分只作用于主体（2026-11-06 用户口径）

- 规则：范围/爆炸伤害里的**元素成分**（毒/燃烧/冰冻/电击/眩晕/恐惧/辐射/骇入/催化）不作用于肢体，只作用于主体。
- 起因：`FpsHelper.Hit` 爆炸分支是**按部位循环**、每个 `Damageable` 各发一份包，而肢体经
  `GetComponentInParent<IHealth>()` 共用**主体那管 Health** ⇒ 元素伤害与异常积蓄被部位数放大 N 倍
  （Dec_Ultralisk 29 个部位 = 29 倍）。
- 落地三处：
  1. `00GameContract/Data/DamagePacket.cs` 新增 `AreaHit`（含义：本次结算会给同一单位**每个部位各一份包**）；
  2. `06Gameplay/Common/FpsHelper/FpsHelper_Hit.cs` 爆炸分支 `AreaHit = true`；
  3. `05UnitCore/Damage/Damageable.cs`：`dropElement = packet.AreaHit && !isMain && Health.GetMainPart().IsValid()`
     ⇒ 成分循环里 `IsElementType(item.Key)` 直接 `continue`；若那份包只剩元素则 `settledGroups.Count == 0` **提前 return**
     （否则会派发 0 伤害的 `OnSettled`/上报）。
- ⚠ 判据**必须**带 `Health.GetMainPart().IsValid()`：只写 `!isMain`，遇到"没配 MainPart 的多部位单位"
  （实测 `Dec_FlyTitan` 32 个 Damageable、`MainPart` 为空）会把所有部位都当肢体 ⇒ 元素伤害整段丢光。
- ⚠ 刻意**不**用 `!packet.isDirect` 判范围：远端镜像包（`EnemyNetBridge` / `ShieldBag`）的 `isDirect` 默认 false，
  会被误当成 AoE ⇒ 两端元素口径不一致。也**不**给 `HitAreaKinetic`（踩踏/圣水）和电磁尾迹置 `AreaHit`：
  这两条路径"每单位只取最近的一个部位、只结算一次"，置了元素就真丢了。
- `Destruction`（护甲破坏）**不算元素**（肢体也有护甲），`Real`（溶解）属白名单 ⇒ 都照旧作用于肢体。
  `IsElementType` 写成枚举白名单，别改成"除动能/爆炸/溶解以外都算元素"，否则以后新增的结构类成分会被误丢。
- 联机一致性：开枪端已经把肢体那份的元素剥掉了，4025/4040 上报的就是剥离后的数值 ⇒ 对端 `Resolved` 包不用再判一次。
