## Turret 新增「同轴炮塔」类型（Coaxial）

- 需求：只登记一个绑定武器供控制器触发起火，**不处理任何旋转**（瞄准交给本体朝向）。
- 改动：
  - `Turret.TurretType` 追加 `Coaxial`（**加在末尾**，保持 prefab YAML 里 `type: 0/1` 的旧值不变）。
  - `Turret.IsCoaxial`；`Init` 里同轴分支：必须有 `weapon`（否则一条 LogError + return）、补 `weapon.Owner`、`dot=1`，**不再要求 chassis/barrel**。
  - `Look/Rotate/Aiming/Synchro` 首行 `if (IsCoaxial) return;`——否则 `chassis` 为 null 时 `Synchro/Aiming` 直接 NRE。
  - `IsLockTarget` 对同轴**恒 true**：不同轴就没人算 `dot`，dot=0 ⇒ `(1-dot)>=allowDeviation` ⇒ 控制器永不开火（这是唯一真正的坑）。
  - 新增 `Turret.FirePosition`（`chassis ? chassis.position : firePoint→root`）：同轴没底盘，`CanFireAt` 与各控制器的射程判定改用它；`SimpleTurret.TryAtack`、`GuardDog.TryAtack` 原本直接取 `turret.barrel.position`（同轴下是 null）已替换。
  - `AimDir()` 同轴取 muzzle forward；`DrawGizmosSelected` 同轴只画发射点射线。
  - `TurretDrawer`（`Editor/TurretDrawer.cs`）新增同轴分支：摘要只显示"武器✓/✗"，结构只画绑定武器，参数只留 开火延迟 + 最小攻击距离；展开 6 行（`GetCoaxialLineCount`）。
- 验证：`offline_compile.py 06_Gameplay` 0 error（drawer 也在该程序集内、UNITY_EDITOR 有定义）；BOM/LF 均保持。

### 补充（同日，用户要求）：同轴炮塔必须有"炮口"来做瞄准判定

- 追加字段 `Turret.muzzle`（`[InspectorName("炮口(同轴瞄准判定)")]`），留空回退 `firePoint`（`MuzzleRef`）。
- `Look()` 同轴分支改走 `LookCoaxial()`：**不再**恒锁定，而是量 `muzzle.forward` 与炮口→目标夹角算 `dot`；
  `dot` 取 `cos(θ/2)`（= `sqrt((1+cosθ)/2)`）而不是 `cosθ`，这样**同一个 `allowDeviation` 阈值**与其它类型的 `Quaternion.Dot` 口径一致（默认 0.005 ≈ 11.5°）。
- 于是 `IsLockTarget` 恢复成统一公式，删掉了「同轴恒 true」；`Init` 里同轴的 `dot=1` 也删了（初始不锁定，Look 每帧刷新）。
- ⚠ 顺序保证：所有控制器都是同帧先 `AimTargrt()→Look()` 再判 `IsLockTarget` 开火，所以 dot 一定是本轮新鲜的；若以后有人先开火后 Look，就会慢一帧。
- Drawer 同轴面板：结构 = 绑定武器 + 炮口；参数 = 开火延迟/最小攻击距离 + 允许偏差(弧度)；展开 8 行。

### 修正（同日）：不要新开 muzzle 字段，复用 `barrel`

- 用户判断：同轴本来就不旋转，`barrel` 字段在同轴下只当参考点 ⇒ **删掉新增的 `muzzle` 字段与 `MuzzleRef`**，同轴的炮口就是 `barrel`。

## 诊断：FastTest 场景 `TerrainUtils.AsyncRefresh` NRE（TerrainClearer NavMesh 腿）

- 结论：`TerrainUtils.nav` 为 **null**。`nav` 只在 `Main` setter 里用 `value.transform.GetComponentInParent<NavMeshSurface>()` 取（TerrainMainUtils.cs:70），要求 NavMeshSurface 在**地形自身或祖先**上。
- FastTest 的层级违反该假设：`MapRoot`（tag MapRoot，挂着 `Unity.AI.Navigation.NavMeshSurface`，navMeshData=Assets/Scene/FastTest/NavMesh-MapRoot.asset）是根，子物体只有 `Day-Night-Manager`/`Halo`；`Terrain` 是**另一个独立根**（parent=null），`MapRoot.terrain` 指向它 ⇒ 取不到 surface。BattleScene 里 Terrain 是 MapRoot 子物体（fileID 1376797504 在 MapRoot 的 m_Children 里）所以不炸。
- 触发链：`TerrainClearer.Process`（地形脏）→ `RefreshNavLeg`（TerrainClearer.cs:461）→ `AsyncRefresh(true)`（TerrainMainUtils.cs:850）抛；异常发生在 `_navDirty=false`（TerrainClearer.cs:439）之前 ⇒ 脏标记不被消费，每 `NavRefreshInterval` 重复抛，且 NavMesh 永远不重烘。
- 同隐患：`MissionController.cs:127` 也直接 `AsyncRefresh(true)`（FastTest 走 FindFromScene 分支才没踩到）。
- 修法二选：① FastTest 把 Terrain 拖进 MapRoot 下（与 BattleScene 一致）；② 不靠层级推断 —— 由 `BattleManager` 设 `Main` 时显式把 `mapRoot.GetComponent<NavMeshSurface>()` 传给 TerrainUtils（推荐，避免下一个场景同样踩）。

## Tank_Siege 迫击炮"半空自爆"（离地约 3m 爆炸+特效）诊断 → 已修

- 现象：高抛炮弹飞到一半（y≈3）就炸，还是先有爆炸特效。
- 实测证据（Play 暂停时反射读运行实例，`Projectile_ShellHead_Green(Clone)`）：`Owner=Tank_Siege`、`WeaponBase=RobotWeapon_Mrotar`、
  `InitialPosition=(29.63,4.34,1.05)`、`m_LifeTime=2`、`m_isStop=false`、已回池、
  `m_Velocity=(-17.77,-151.41,-2.00)` = 初速 `(-18,148.5,-1.5)` 经 `Gravity 150` **整 2.0s** 恰好累加出来的值。
- 结论：**不是撞到东西，是生命引信到点**。`ProjectileStandard.DelayedRelese(2s)` → `OnHit(BuildHitData(pos, forward))`（collider 为 null）
  → `FpsHelper.Hit` 照旧按 `ImpactVfx` 播爆炸 → 看起来就是"半空自爆"。`m_isStop=false` 也是这条路径的指纹（不是 Hit 停弹）。
- 物理根因：`Speed=150 / Gravity=150` ⇒ 弹道理论最长飞行时间 `2v/g = 2.0s`，而 `DamageData.MaxLifeTime` 正好也是 **2**
  ⇒ 高抛解（θ≈83°，36m 距离）落地时刻≈引信时刻，永远差 0.02s 在 3m 高被点爆。弹道本身没问题（落点距玩家约 10m，玩家 2s 内移动）。
- 修复（`Assets/Resources/Prefabs/Enemy/Robot/PMC/Tank_Siege.prefab` 变体覆盖，脚本 `.codebuddy/plans/_fix_tank_siege_fuze.py`）：
  `MaxLifeTime 2 → 6`（同族 `Tank_Mortar` 也是 6，留 3x 余量）+ 显式 `MaxRange = 300`
  ⚠ 必须显式写 MaxRange：`MaxRange=-1` 时 `CurrentWeaponRange = MaxLifeTime*Speed`，只改寿命会让它从 300 变 900 ⇒ AI 交战距离被一起放大。
- 口径：`Tank.prefab` 基体的迫击炮是 `Speed500/Gravity10/MaxLifeTime1`（直线弹、500m 射程自洽）；
  **改 Speed/Gravity 必须重算寿命**（v 变小、g 变大都会让 `2v/g` 变大）。
- 顺带澄清：未提交的 `ProjectileStandard.IsHitValid` 自碰撞过滤**不是**本次症状的原因（该炮 `MinRange=5` 已屏蔽出膛自撞），属额外健壮性改动。

## 巢穴任务奖励"配 50 结算只给 2"（已修为每座独立）

- 现象：`PMCNestDecS.asset`（拆毁营地，`reward={50,50}`）打完结算只给 2 青辉石；任务完成弹窗却显示 50。
- 根因：`06Gameplay/Events/TaskData.cs` 的 `SelectTaskData.NestReward` 里 `nests[i].Sum(item=>item.complete?1:0*item.reward) / nests[i].Length` —— `?:` 优先级低于 `*`，实际是 `complete?1:0`，再整除组内总数 ⇒ 每组只有 0/1 分，`TaskItem.reward`（= `cfg.reward.x`）从未参与。
- 上限即"非空组数"（`nestCount` 固定 3 档：Small{4,0,0}/Medium{3,1,0}/Large{2,2,1}）⇒ 用户拿到 2 = Medium 两组全清。
- 用户拍板口径 **B：每座独立，清一座给该座 reward**（非组内平均）。改法：去掉 `/ nests[i].Length`，`item.complete ? item.reward : 0`。
  ⇒ 满清：Small/Medium = 4 座 = 200，Large = 5 座 = 250；`GameEndWnd` 四处显示与 `/5` 经验都读属性、自动跟随；`MissionCompleteWnd.cs:80` 显示单座 reward(=50)，与 B 一致，无需改。
- ⚠ 教训：C# `?:` 优先级最低（仅高于赋值），`a ? 1 : 0 * b` 永远不是"按 b 取值"；写这类奖励公式别用紧凑三元 + 乘法混排。

## 巡逻队权重 >100 的口径（诊断，未改代码）

- `CreatPatrol` 里 `Patrol.WeightTake(100, patrolRandom)`（`09Manager/Battle/WaveManager.cs:746`）**总权重写死 100**；
  而同文件 `TierWeight`/`TierItemWeight` 都是现算总和（:467-470、:552-555 注释明写"别写死 100"）⇒ 只有巡逻队这一处没跟上。
- `WeightTake`（`00Tools/IEnumerableUtils.cs:12-24`）：`Range(1, total+1)` → 顺序累加 → `randomValue < v` 命中 → 末尾 `return list[0]`。
  - **总和 >100**：不报错；游标上限 100 ⇒ **第一个累计和 ≥100 的项吸收全部剩余概率，它之后的模板概率恒 0（永远抽不到）**。
    例 `[30,30,30,30]`(120)：末项 30%→11%；`[60,60,40]`(160)：第三项 0%；`[150,50]`：第二项 0%。
  - **总和 <100**：落空区间（如总 80 ⇒ 掷到 81~100）全塞给 `list[0]`，第一项被抬高。
  - off-by-one：判据是 `<` 不是 `<=` ⇒ 每项实际区间 `[prev+1, v-1]`；总=100 的 `[50,50]` 实际 49%/51%。
- 结论：权重表按"百分比基准 100"设计才自洽；改法 = 现算总和。
- **已修（2026-11-25，用户要求"按总和算 + 开局算一次"）**：`WaveManager` 新增 `int _patrolTotalWeight`，
  在 `Awake` 里 `Patrol` 构建后一次性累加（`WaveCont` 是 `BattleManager` 的场景引用 ⇒ 一局一个实例、Awake 只跑一次）；
  `CreatPatrol` 改用该值，并在 `<=0`（= `Patrol` 为空，即模板名与 `patrolCfgs` 对不上）时 LogError + 返回空表，
  避免 `WeightTake` 的 `list[0]` 越界。`randomValue < v` 的 off-by-one 未动（属全仓通用工具、会改所有随机序列）。

## Tank 变体纹理"一受击就变回原样"（已修 `10_Effect/ApplayMapTextureVariant.cs`）

- 现象：`Resources/Prefabs/Enemy/Robot/PMC/Tank.prefab` 的 `ApplayMapTextureVariant` 生成时正确换了 `_BaseMap`，
  一挨打就永久变回默认（且不会自己恢复）。
- 根因：变体纹理写的是**渲染器级** MPB（`SetPropertyBlock(block)`，下标 -1）；`FxControllerBase` 的受击闪白/溶解走
  `RendererSlot.Flush → SetPropertyBlock(mpb, MaterialIndex)`，两套存储 ⇒ 一旦某下标有了块，渲染器级那块对该下标**永久失效**，
  而槽位块里只有 `_HitColor`/`_DissolveValue`，没有 `_BaseMap` ⇒ 落回材质自带贴图。与 `BattleApplyVehicleData`（机甲皮肤）同一个坑。
- 修法（照 `BattleApplyVehicleData.StampSkinToSharedSlots` 抄）：`ApplayMapTextureVariant` 保留渲染器级写入，
  再用协程等一帧（槽位表在 `FxControllerBase.Start` 的 `InitFx` 才建）→ `fx.GetSharedSlotBlock(r,k)` 写 `_BaseMap` + `MarkSlotDirty`，然后 `Destroy(this)`。
- 印证：`Tank.prefab` 的 `BirthMaterial` 为空 ⇒ 与诞生材质还原无关；`EFD_Enemy.asset` 两条受击/死亡条目 `material` 留空 ⇒ 走 `fxMaterial=Vox_PMC.mat` 建槽。
- 验证：`offline_compile.py 10_Effect` 0 error；BOM OK、行尾保持 LF。
- ⚠ 通用口径：**任何"按 index Flush 的瞬时 MPB"都会吃掉别人写在渲染器级的长期属性**；长期外观（变体贴图/皮肤）必须写共享槽位块。
