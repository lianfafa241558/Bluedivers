# 联机 · 关键物体位置同步 系统设计计划

> 状态：**只做设计，未动任何代码/资产**（2026-10-06）
> 上游：`联机_房间列表接入与KCPNet扩展_计划.md`（房间/入房/扩 DTO 已完成）
> 本次回答的问题：战斗里"关键物体"的位置怎么同步。

---

## 0. 结论先行（选型）

**不做帧同步 / 确定性重演（Deterministic Lockstep），做「房主权威 + 事件驱动生命周期 + 分级频率快照插值」。**

| 维度 | 选择 | 一句话理由 |
| --- | --- | --- |
| 权威模型 | **房主全权威**（敌人 AI / 伤害 / 生成） | 局域网星型拓扑，成员↔房主，天然有中心 |
| 生命周期 | **事件同步**（Spawn / Despawn） | 现行随机体系无法跨端复现生成结果（见 §1） |
| 位置 | **快照 + 插值**（10Hz 上行、渲染延迟 ~150ms） | 不需要逐帧对齐；人眼对 100~200ms 插值不敏感 |
| 玩家位置 | 各端**自治自己**，上行房主 → 房主转发 | 玩家输入手感必须本地 0 延迟 |
| 抛射物/子弹 | **不同步**（本地预测，最多同步"开火事件"） | 弹道毫秒级、数量大，同步性价比最低 |
| 时间轴 | **复用 `NetManager` 的 50Hz 逻辑帧** | 项目已备好，注释明说就是给联机留的（§2.4） |

## 1. 为什么不能靠"同种子确定性重演"（硬证据）

结论：**种子能保证的只有"开局那一刻"，动态物一定会漂移。**

> ⚠ 先纠正一个容易说错的归因：**这**不是"随机数"的问题，而是"**驱动源**"的问题**。随机只是最先崩的那一层。

### 1.1 失败分三层（由浅到深；只有第一层是"随机"）

| 层 | 内容 | 可修性 |
| --- | --- | --- |
| **L1 随机层** | 4 类非确定随机源 | 可修，但**单独修它没用** |
| **L2 时序层** | 变步长积分 + Unity `Update` 顺序 + 协程/`Invoke`/`Time.time` | 可修，但伤筋动骨 |
| **L3 引擎层** | `NavMeshAgent` / `CharacterController` / `Physics` | **几乎不可修**（Unity 不保证跨实例确定性，同机双开都不保证） |

**L1 · 4 类非确定随机源**

1. **全局共享静态流**：`RandomUtils.cs:14` 是**全进程唯一**的 `System.Random`（默认用 `DateTime` 播种），任何系统调用都会推进它 ⇒ "谁先调用"决定后续所有结果。
   - 同一段静态流被**玩法多处**消费：`CreatOOPart.cs:18`、`CreateSupple.cs:21`、`PropertyManager.cs:38`、`MissionBase.cs:292`、`WeaponBaseController.cs:456`，以及**密码锁** `KeyScreenControl.cs:65/69/236-239/333-334/518`。
2. **`UnityEngine.Random` 旁路（完全未接入种子）**：武器散布 `WeaponBaseController.cs:591`、`WeaponController.cs:897`、`WeaponPlayerController.cs:241`；AI 环绕角 `EnemyMobile.cs:809`；毒性游荡 `EnemyMobile_AboState.cs:158`；掉落 `DieLoot.cs:21`；NPC 游荡 `NPCWalk.cs:98-101`。
   - ⚠ **武器散布是"每次开火都消费"** ⇒ 两端开火次数/时机不同，必然分叉。
3. **帧驱动消费**：`CreatEnemy.cs:80`（每帧 `BattleRandom.Bool`）、`EnemyNestBuild.cs:56/77`、`UnitSkill_Blink.cs:21`、`DetectionModuleAirdrop.cs:63/83`、`Furniture_PlayerArtillery.cs:89/151`。
4. **时间节流旁路**：`EnemyController.cs:158`（`Invoke(nameof(BirthEnd), ...)`）、`HealthPlayer.cs:47`（`InvokeRepeating`）、`FxControllerBase.cs:196`（`Time.time` 节流）。

> 只要**有一处**消费次数不同，之后所有随机结果**整体错位**——这正是 lockstep 最怕的"不同步"。而且本项目**已经依赖**这种一致性：`KeyScreenControl.cs:67` 的注释写着"同步保证每个人一样"（密码锁的目标序列），`WeatherSystem.cs:41` 写着"使用 BattleRandom 时同种子结果确定"⇒ **作者当年就是奔着确定性去的**（见 §1.3）。

**L2 · 时序层**

- 积分混用**变步长**：`BaseSelfMoveableController.cs:536/553/587-611` 在定点量（`PEVector3`）上做 `Vector3.Lerp(..., Time.deltaTime)` / `Mathf.Exp(-drag * Time.deltaTime)` ⇒ 即使数值类型是定点，**步长是浮点且帧率相关**。
- Unity **不保证**同帧内各 `Update` 的调用顺序（除非设 Execution Order）；AI 状态机在 `Update`（`EnemyController.cs:163`、`StateMachineFrame.cs:87-90`），逻辑帧又在 `NetManager.Update`（`NetManager.cs:65`）⇒ 两套时序混跑。

**L3 · 引擎层（死结所在）**

- `PathRequestManager` 只是转发 `NavMeshAgent.SetDestination`（`PathRequestManager.cs:91`），**真正的移动与避障在 Unity 内部**（含 RVO 局部避让、浮点积分、`pathPending` 异步完成时机）。
- 于是：**同一个 agent、同一个目标点，两台机器上的位置也会有微差**；微差 → 下一次路径重算的输入不同 → 差异被放大（指数发散）。几秒内就能从"厘米级"涨到"几十米"。
- 再加上 `CharacterController` 的胶囊扫掠与 `Physics` 查询（21 个文件用了 `CharacterController`/`Rigidbody`）。

### 1.2 工程判断：**半确定性比不确定性更危险**

如果一部分系统走种子、另一部分走快照，bug 会表现为"偶尔不一致/偶尔卡住"——**最难查的一类**。所以只有两种干净形态：
**(a) 全快照（推荐）**，或 **(b) 全锁步**。
"局部确定性"必须被限制在**边界清晰、只跑一次**的区间内（下文的档 B）。

### 1.3 好消息：项目里已有"确定性半成品"，不用从零救

| 已具备 | 证据 | 意义 |
| --- | --- | --- |
| 50Hz 逻辑帧宿主 | `NetManager.cs:20-31`，注释明说"就是给联机留的" | tick 不用新造 |
| **定点数学层** | `Assets/Plugins/PEMaths/PEMaths.dll`（`PEInt`/`PEVector2/3`/`PEMath`，`PEInt.RawFloat` 文档写"转换完成后不可再参与逻辑运算"） | 逻辑侧已有确定性数值类型 |
| 定点已用于**玩法核心** | 速度 `BaseSelfMoveableController.cs:107/766/772`；伤害/爆炸 `FpsHelper_Hit.cs:59-62/203/225/373`；空间查询 `UnitQuery.FindUnits(new PECircle(...))`；逻辑位置 `Actor.LogicPos`/`Logic3Pos` | 不是装饰，是真在用 |
| 每局种子链路完整 | `TaskCfg.seed` → `BattleManager.cs:111/164` → `StartGameNtf.Seed` → `TeamManager.SetSeed` → `RandomUtils.InitRandom` | 种子能传到对端 |
| 作者心迹 | `WeatherSystem.cs:41`、`KeyScreenControl.cs:67` 的注释 | 原设计目标就是确定性 |

⇒ 精确结论：**"确定性"在本项目是"没走完"，不是"走不通"**。缺的是最后三块拼图：逻辑帧没接管 AI、积分里混了 `Time.deltaTime`、随机有旁路（L1 的四类）。

### 1.4 能不能救：三档方案

**档 A · 全量 lockstep（可救，但要重写模拟层）**

必做 7 件事（缺一不可）：

1. **单一固定步长**：AI/移动/武器冷却全部搬进 `LogicTick`（现状 `EnemyController.Update:163`、`StateMachineFrame.Update:87-90`、`WeaponBaseController : LogicBehaviour` 混用）；
2. **积分去 `Time.deltaTime`**：`BaseSelfMoveableController.cs:536/553/587-611` 改定步长；`PEVector3.RawVector3 ↔ Vector3` 的来回转换全部清理；
3. **运动脱离 Unity 导航/物理**：`NavMeshAgent` → 自研网格寻路（或"路径由房主算好下发"）；`CharacterController` → 定点胶囊扫掠（⚠ 需先确认 `PEMaths` 有没有 capsule sweep 能力）；
4. **随机全面确定性化**：`RandomUtils` 拆成**每实体/每用途独立流**；`UnityEngine.Random` 全部替换（武器散布/AI 环绕/掉落/NPC）；
5. **消除帧序依赖**：`Invoke`/协程/`Time.time` 节流 → tick 计数；
6. **定点化到底**：`PEInt.RawFloat` 只允许出现在表现层；
7. **构建一致性**：同后端（IL2CPP/Mono）、注意 `Unity.Burst`（被 `06_Gameplay` 引用）与浮点行为差异。

> **验收判据（先写测试再动手）**：同种子 + 同输入序列，跑 N=3000 帧后，所有实体 `LogicPos` **逐位一致**。这条过不了，档 A 立即止损。

**档 B · 局部确定性（推荐 —— 这才是"真正能救回来"的部分）**

把确定性**收缩到"只跑一次的初始化层"**：

| 收进确定性区（走种子，不占带宽） | 踢出到快照区（房主权威） |
| --- | --- |
| 地形/静态布局（地形本身就是种子生成） | 刷兵（`CreatEnemy.cs:80` 每帧判定） |
| 任务点/兴趣点/场景点（`MissionController`） | 敌人 AI 移动与决策 |
| 建筑/采集物/补给（`EnqueueInit` 段） | 武器散布/弹道 |
| 初始波次编成（`WaveManager.InitWaveUnits`） | 掉落、天气**变化** |
| 开局天气（`RandomWeather()`） | 密码锁之外的运行中随机 |
| **密码锁目标序列**（`KeyScreenControl.cs:65-70`） | |

**三条前提**（都要实测，缺一条档 B 就不成立）：
1. **初始化顺序跨端一致**：`BattleManager.Init/InitSpecial` 是**协程 + `yield return null` + `WaitForInitialization()`**（`BattleManager.cs:104-158`），帧边界会插入 —— 需确认这段期间没有别的随机消费者抢跑；
2. **期间无旁路消费**：审计从 `BattleRandom = new(seed)` 到 `DrainInitQueue()` 之间所有 `BattleRandom`/`RandomUtils` 消费点（已知：`MissionController`、`WaveManager`、`PatrolContriller`、`AirdropController.Init`、`RandomWeather`、`CreatOOPart/CreateSupple/CreateBuilding`）；
3. **静态流隔离**：给"必须一致"的用途**派生独立流**，不再共用全局静态流。做法（便宜且立刻见效）：
   ```csharp
   // 不再吃 RandomUtils 的全局流（会被密码锁/武器/掉落偷走一段）
   var r = new System.Random(unchecked(seed * 31 + (int)purposeId));
   ```
   ⇒ 立刻切断 `KeyScreenControl`↔`CreatOOPart` 这类互相偷随机的耦合。

**收益**：静态物**完全不用同步**（省掉 §2.1 表里所有 P1 静态项），且密码锁这类"必须两端一致"的玩法恢复稳定。

**档 C · 输入锁步（Command lockstep）**：以档 A 为前提；本项目运动是 NavMesh + 物理驱动，档 C 不解决底层问题，**不适用**。

### 1.5 判据：什么时候才值得上档 A

| 项目现状 | 结论 |
| --- | --- |
| 4 人、局域网、P2P 房主 | **快照方案（§3）性价比碾压**：带宽 ~2.8KB/s，无重写风险 |
| 若将来要：8 人以上 / 极低带宽 / 录像回放 / 裁判服 | 才考虑档 A，且必须先过 §1.4 的"逐位一致"验收 |

**⇒ 本计划采用：档 B（初始化层确定性）+ 动态物快照。** 这与 §3 的设计不冲突，而是**去掉它最大的一块同步包袱**。

### 2.4 时间与帧来源（已现成，复用）

`NetManager`（`09Manager/Global/NetManager.cs:20`，挂在 GameRoot，实现 `I_GlobaManager`）就是 50Hz 逻辑帧宿主，其注释原文：

> 本类最初是为**联机**准备的（"帧该由服务器 / 房主下发"）……**将来真做联机时只需把"帧来源"从本地时钟换成网络帧，本类结构与接入方（`LogicBehaviour` 子类）都不受影响。**

⇒ **不新造 tick**。房主每逻辑帧递增 `HostTick`，快照按 tick 取模发送。

## 3. 系统设计

### 3.1 三层结构

```
┌─ 身份层 ──────────────────────────────────────────────┐
│ NetId（uint）= (sid << 24) | seq     房主统一分配      │
│ NetObjectRegistry（02_Net，纯数据）：NetId ↔ GameObject │
└───────────────────────────────────────────────────────┘
┌─ 权威层（09_Managers/NetBattleBridge）────────────────┐
│ 订阅 UnitEventSub.* → 决定"谁生成/谁上报/谁应用"       │
│ 实现契约层的生成门 → 玩法层查询"我该不该本地生成"      │
└───────────────────────────────────────────────────────┘
┌─ 传输层（02_Net/NetBattleFlow）───────────────────────┐
│ Spawn/Despawn 事件（可靠） + 位置快照（10Hz，丢旧）    │
│ 编解码：手写 byte[]（不走 MessagePack，见 §8 风险 4）  │
└───────────────────────────────────────────────────────┘
```

### 3.2 身份：`NetId`（**不能用 `Actor.IndexID`**）

- `Actor.IndexID` 是各端自增计数器（`Actor.cs:24 / 206`）⇒ 各端实例化顺序不同，**编号必然不一致**，不能当网络 ID。
- 分配规则：`NetId = (sid << 24) | (++seq)`，**由房主统一分配**（`sid = 0` 表示房主自己生成的场景/波次物体）。高位分段保证"成员本地生成的自己的角色"也不会撞号。
- `NetObjectRegistry`（放 `02_Net`，只依赖 `GameObject/Transform`，**不碰 `Actor`**）：
  - `uint AllocHostId(uint sid)` / `bool TryGet(uint netId, out GameObject go)` / `bool TryGet(GameObject go, out uint netId)` / `void Unregister(uint netId)`
  - ⚠ 用 `Dictionary<uint, GameObject>` + 弱引用校验（`go == null` 即已销毁，顺手清表）。

### 3.3 权威划分（谁模拟、谁上报、成员端干嘛）

| 物体 | 模拟方 | 成员端行为 |
| --- | --- | --- |
| 自己的角色 | **本机**（输入 + 物理） | 位置 20Hz 上行房主；房主转发给其他人 |
| 别人的角色 | 对方本机 | **禁输入**，位置插值；碰撞体保留（本地命中判定仍要生效） |

### 3.5 位置快照（分桶 + 量化 + 丢旧 + 插值）

**节奏**：逻辑帧 50Hz（`NetManager`）→ **快照 10Hz**（每 5 tick 一批）；玩家位置 20Hz（手感优先）。

**单条记录 10 字节**：

| 字段 | 位数 | 说明 |
| --- | --- | --- |
| `netId` | uint16 | ≤ 65535 实体（实际 < 2k） |
| `pos.x/y/z` | 3 × int16 | 量化 **0.05m** ⇒ ±1638m（**地图尺寸待确认，见 §7 决策 5**；超界改用"块原点 + 局部偏移"） |
| `yaw` | int8 | 1.4°/格；`pitch` 不同步（表现层本地算） |
| `flags` | 1B | 静止 / 死亡 / 传送（传送 = 不插值、直接 snap） |

**带宽预算**：

| 场景 | 计算 | 结果 |
| --- | --- | --- |
| 20 敌人 + 4 玩家 | 20×10B×10Hz + 4×10B×20Hz | **≈ 2.8 KB/s** |
| 200 敌人（压力） | 200×10B×10Hz | ≈ 20 KB/s（**2000B/快照 ⇒ 拆 2 包**） |

包结构：`[tick:4B][count:1B][n×10B]`，单包 ≤ 1200B（UDP 安全 MTU）⇒ 每包最多 ~119 实体。

**分桶（round-robin）**：按 `netId` 哈希到 K 个桶，每 tick 发 1 个桶 ⇒ 峰值包大小可控，且**每个实体都能拿到稳定频率**。

> ⚠ **KCP 是可靠有序流**（库只给了 KCP 通道，没有不可靠通道）⇒ 丢包重传会让**旧快照晚到**，出现"回退抖动"。
> 对策（应用层，必须做）：
> 1. 快照带 `tick`，接收端 **`if (snap.tick <= lastAppliedTick) return;`**
> 2. 发送端**只发最新值**（不排队历史帧）
> 3. 快照与事件（Spawn/Despawn/伤害）**分优先级**：事件立即发，快照受"每 tick 字节预算"约束

**编解码**：手写 `byte[]`（`NetSnapshotCodec`），**不用 MessagePack** —— 高频 + IL2CPP AOT 反射解析器风险（§8 风险 4）。

### 3.6 插值 / 外推

- 缓冲 **2 个快照**，渲染延迟 ≈ `2 × 快照间隔` ≈ **200ms**（局域网可调至 1 个 = 100ms）
- 采样：相邻两帧**线性插值**（位置）+ `Slerp`（朝向）；速度可用"两帧差/Δt"外推（最多外推 1 帧，防穿透）
- **快照阈值**：误差 > 4m 或 `flags.传送` ⇒ **直接 snap**（避免"滑行进墙")
- 静止优化：`flags.静止` 的实体降到 2Hz（省带宽大头）

### 3.7 伤害 / 死亡一致性（位置同步的**必要伴生项**）

不做这条，位置同步就是"看别人家的兵在自己屏幕上走动，打不死"。

**推荐方案 A：房主裁决**

```
成员开枪命中 → HitReq{ shooterNetId, targetNetId, part, damage, hitPoint } → 房主
房主校验（目标存在 / 未死 / 距离合理）→ 应用伤害（权威 Health）
              → DamageNtf{ targetNetId, hp, isDead } → 广播全体
成员端：本地立刻播"命中特效/音效"（表现层预测），血量条等 DamageNtf
```

- 优点：零对账、无回滚；局域网 RTT/2 ≈ 5~20ms，手感影响可接受
- 备选方案 B（本地判定 + 房主对账修正）：复杂、易抖，**不建议本轮做**
