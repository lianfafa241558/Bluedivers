**让成员侧与房主侧走"同构"的开局管线**：`SetTask →（加载战斗场景）→ BattleManager.Creat`。

### R2 ⚠⚠ 开局后必须停止"重排名单" —— **即使禁止进人，掉线路径依然会触发**

> 用户判断"开始战斗后应当禁止进人 ⇒ 不会出问题"。**方向对，但漏了一条路径**：
> `NetHostSvc` 有 **4 处**广播名单，其中**掉线**这条路在战斗中照样会走。

| 广播点 | 触发条件 | 战斗中会发生吗 |
| --- | --- | --- |
| `OnJoinRoomReq` → `BroadcastPlayerList()` | 有人入房 | ❌ 禁止进人 ⇒ 不会 |
| `OnReadyState` → `BroadcastPlayerList()`（`:358`） | 准备状态切换 | ❌ `SetReady` 由舰桥 UI 触发，战斗中 `BridgeSys` 已销毁 |
| `OnPlayerProfileNtf` → `BroadcastPlayerList()`（`:385`） | 资料变更（切角色/战备） | ❌ 同样只在舰桥 |
| ⚠ **`OnMemberLeft`（`:274-286`）/ `OnLeaveRoomNtf`（`:336-344`）** → `BroadcastPlayerList()` | **成员断线 / 主动退房** | ✅ **会** —— 掉线不挑场合 |

**而且它比"重排"更狠：列表会少一个人** ⇒
- `ArmamentWnd` 的 `armamentRoot.GetChild(i)` ↔ `players[i]` 假设直接被破坏
- ⚠ **`task.BattleData` 与 `players` 的长度耦合**：`TaskManager.cs:393-397` 开局按 `players.Count` 逐个 `BattleData.Add(...)`；而 `BattleManager.AddBattleDataItem(playerIndex, name)` → `MissionCont.AddBattleDataItem(...)` 是**按下标**写的 ⇒ 战斗中列表变短 ⇒ **统计/结算错位或越界**

**改法（双保险，各 2~3 行）**
```csharp
// ① 成员侧（09Manager/Global/TeamNetBridge.cs::HandlePlayerList 入口）
if (FPSGame.Data.BattleState.IsStartBattle)
{
    // 只按 id 找到既有 PlayerData 更新资料字段（名字/角色/战备…），不动顺序、不动 players.Count
    return;
}
team.ReplacePlayers(order);

// ② 房主侧（NetTmp/Client/NetHostSvc.cs::BroadcastPlayerList 入口）
if (_started) return;    // _started 已在 StartGame() 里置 true（:434）⇒ 开局后不再广播名单
```
- `BattleState.IsStartBattle` 由 `BattleManager.cs:210` 写入，`BattleState.Reset()` 在每局 `Awake`（`:291`）复位 ✓ 天然按局生效
- ⚠ 房主侧加了门之后，**掉线玩家的"消失"就不会同步给其他人** ⇒ 这是有意的（本局名册冻结）；但要在**下一局开始前**恢复同步（`StartGame` 里先 `BroadcastPlayerList()`，见 R3 ⇒ 那一句必须放在 `_started = true` **之前**）

### R3 ⚠ 名单就绪：靠 **KCP 有序** 免费解决

`NetHostSvc.StartGame()` **当前不广播名单**（只 `SendToAll(StartGameNtf)`，见 `NetHostSvc.cs:431-445`）。若成员在开局前恰好漏掉一次 `PlayerListSync`，进战斗时名单就是旧的。

**改法（推荐）**：在 `NetHostSvc.StartGame()` 内部**第一步先 `BroadcastPlayerList()`，第二步再 `SendToAll(StartGameNtf)`**。
- ✅ **KCP 是可靠有序流** ⇒ 成员**必然先收到名单、再收到开局** ⇒ 不需要额外握手/等待
- ✅ `BroadcastPlayerList()` 末尾自带 `MessageCenter.Dispatch(msg)`（`:477`）⇒ 房主本地也刷新
- ⚠ 与 R2 配合：成员收到名单时 `IsStartBattle` 还是 false ⇒ 正常重建一次 ✓；随后开局 ⇒ 之后不再重排 ✓

### R4 ✅ 幂等：加显式 `MatchId`（决策已定）

KCP 重传 / 房主重复点按钮 ⇒ 重复 `StartGameNtf` 会**重复加载场景 + 起两个 `BattleManager`**。

**改法**：`StartGameNtf` 追加 `[Key(7)] public int MatchId;`（房主每次开局自增，从 1 开始；0 = 未指定/旧版）

```csharp
// 房主（NetTmp/Client/NetHostSvc.cs）
private int _matchId;
public void StartGame(…)
{
    BroadcastPlayerList();          // ← 必须先于 _started = true（见 R2②/R3）
    _started = true;
    var ntf = new StartGameNtf { …, MatchId = ++_matchId, TaskFingerprint = fp };
    SendToAll(MessageCenter.Pack(CmdId.StartGameNtf, ntf));
}

// 成员（09Manager/Global/TeamNetBridge.cs::HandleStartGame 入口）
if (ntf.MatchId != 0 && ntf.MatchId == _handledMatchId) return;   // 同一局重入 → 忽略
_handledMatchId = ntf.MatchId;
```
并额外兜一层：`if (GameRoot.GameState == GameStateEnum.Game || _loading) return;`

✅ **`MatchId` 相比用 `seed` 做键的实质好处：免除了"回大厅清键"这个坑** —— 下一局的 `MatchId` 必然不同 ⇒ 不需要在回大厅时手工复位（seed 则可能撞车，见 §7）。

📌 **附带设施**：`MatchId` 也是"以后所有战斗消息都带局标识"的基础 —— 位置同步的快照/事件包里带上它，就能**直接丢弃上一局的残留包**（本局中途断线重连、或房主重开一局时尤其有用）。建议这个字段从一开始就按"公共字段"对待。

### R5 说明：`SetTask` 在大厅调用的副作用是**与房主对称**的，先接受

`SetTask` 末尾会 `GameRoot.GameState = Ready`（`TaskManager.cs:399`）并 `WndManager.Instance.CreatCountDown(...)`（`:401`）。房主也是"先 Ready 再加载场景"，所以成员照做即为对称。
- ⚠ 已知副作用：`BridgeRoleManager.cs:76-80` 在 `GameState == Ready` 时会把玩家移到 `ReadyPoint` 并临时禁用/启用 `CharacterController` —— 大厅里同样会发生（房主也一样），**暂时接受**。
- 若实测出问题（例如倒计时 UI 在大厅闪现），再考虑把 `SetTask` 拆成"只配配置（不切状态）"+"切状态"两段。**方案 B，非首选**。

## 7. 不在本方案范围（但要记一条）

**战斗结束回大厅后如何"再开一局"**：`BattleManager.EndGame`（`:513-535`）会加载 `Utnapishitim` 并 `GameState = Bridge`，场景内对象全部销毁，但 `NetSvc`/`NetHostSvc`/`NetRoomFlow`/`TeamNetBridge` 常驻（挂 `GameRoot`）。
⇒ 回大厅后需要重新走"准备 → 开局"流程。逐项确认：

| 状态 | 是否需要复位 | 说明 |
| --- | --- | --- |
| `BattleState.IsStartBattle` | ✅ 自动 | `BattleState.Reset()` 在每局 `BattleManager.Awake`（`:291`）里跑 ✓ |
| 桥里的 `_handledMatchId` | ❌ **不需要** | 这正是用 `MatchId` 而非 `seed` 的原因：下一局 `MatchId` 必然不同 ⇒ 天然放行（若用 seed 做键，同种子会被误判为重入） |
| ⚠ `NetHostSvc` 的**名单冻结标志** | ✅ **每局开头放行** | 见下 —— 这是 R2② 新引入的、最容易漏的一个点 |

**⚠ 名单冻结的"放行点"（R2② 的必然配套）**

冻结不能是永久开关，否则**下一局开始时的名单广播会被自己挡掉**。正确写法：

```csharp
private bool _rosterFrozen;                 // 独立标志（不复用 _started）

private void BroadcastPlayerList()
{
    if (_rosterFrozen) return;              // 局内冻结
    …原有逻辑…
}

public void StartGame(…)
{
    _rosterFrozen = false;                  // ← 新一局：先放行
    BroadcastPlayerList();                  //    让成员拿到最终名单（R3）
    _rosterFrozen = true;                   //    本局正式开始 ⇒ 冻结
    _started = true;
    …
}
```
- ✅ 不需要在"回大厅"时复位 `_rosterFrozen`（下一局 `StartGame` 会自己放行）
- ⚠ **不要复用 `NetHostSvc._started`**：它还参与 `RoomMeta.InGame`（房间列表"是否已开局"）的语义，临时置 `false` 可能被别的逻辑读到
