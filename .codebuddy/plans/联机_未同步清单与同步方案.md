## 2. 关键设计决定（含讨论中纠正的结论）

### 2.1 任务（P1）：静态同步 + 只同步"状态/进度"
- 用 **B（生成序号）**：`MissionController` 协程生成顺序固定 + 本局配置"以内容为准"下发 ⇒ 集合与顺序两端一致。
- 落地：`MissionBase` 加 **`netOrder`**（由 `MissionController` 按创建顺序赋值，**每局归零**，同 `ActorsManager._enemyNetIdSeq` 手法）。
- ⚠ **只同步进度不够**：`MissionBase` 有 `UpdateMission()→MissionUpdate` 与 `OnMissionCompleted` **两个独立出口**，触发型任务（进撤离区/交互完成）不走进度 ⇒ 消息必须带 **State**。
- 成员端要有"不自己判定完成"的门，否则双重触发。

### 2.2 家具（P2）：一处收口 —— 但这依赖一个已验证的前提
- **键**：`SyncId = FNV1a(Id + 位置量化[0.1m])`。
  - ⚠ `Id` **不唯一**（同类家具多实例）⇒ 直接 `Id`、`FNV1a(Id)` **都不行**（hash 不产生唯一性）。
  - ⚠ **键必须在创建时算一次并缓存**，不能每帧重算（家具位移会让键漂）。
  - 运行时生成的家具依赖"位置两端一致"：静态布局走种子派生、玩家行为生成的（空投/建筑）位置来自已同步落点。
  - ❌ 用层级路径代替位置的方案被否（用户口径：直接 `Id + 位置`）。
- **`NumberID` 不能当同步键**：`private static int nowID`（`Furniture_Attached:22`）进程内自增且**从不复位**，还被当本地注册表键（`list[NumberID]`）。项目已有同款结论（`KeyScreenControl:33-36` 用世界坐标量化哈希）。
- **远端重放安全**：现有订阅方自带过滤 ——
  - `PlayerInputHandler.OnOperation` / `PlayerWeaponsManager.OnOperation` 都有 `user == gameObject` 判定 ⇒ 只要把 `user` 传 **Friend 实例**（或 null）就自然早退 ✔
  - `KeyScreenControl`（共享进度）无过滤 ⇒ 正是要处理的 ✔
  - `OperationWnd.RefreshDisplay` 会多刷一次提示，有 `Update()` 轮询自愈 ⇒ 可接受
  - ⇒ **不需要新开"远端事件总线"**（讨论中一度以为需要，核实后否掉）。
- ⚠ 仍需逐类看"操作者个人收益"：`OOPart` 走 `owner.TryGetComponent<PlayerOOPartInventory>`，Friend 上没该组件 ⇒ 自然 no-op ✔；`Furniture_KeiSubmit` 要单独确认。
- `Pyroxene` 语义"捡起即提交"（现行 `OOPart.cs:32-34` 就是直接进共享的 `TaskState.CollectProperty`）⇒ 改成显式走 `SubmitOOPart`/`KeiSubmit` 语义（用户已拍板）。
- **`OnOOPartCollect` / `OnSubmitOOPart` / `OnKeiSubmit` 不再单独同步**：家具交互同步后，远端重放会本地跑同一套逻辑 ⇒ `TaskState` 两端自然一致 ⇒ 任务进度自然一致。

### 2.3 波次 center：改由**房主周期性权威下发**（4039）
- 初始 center 仍用 `WaveStartSync`(4023) 带（两端 100% 一致）。
- 有些波的 center **跟随玩家移动**（"追击"语义）⇒ 各端自己算"最近玩家"会因位姿延迟/插值**翻边**（离散判定）。
- ✅ **定稿**：房主在本波活跃且 `centerGetter` 非空时，~2Hz 广播 `WaveCenterNtf{WaveIndex,X,Y,Z}`（可加"变化 >0.5m 才发"）；**房主本机也写同一个 field**。客户端**只做插值跟随**（`MoveTowards`/lerp）⇒ **判定只存在一处**，观感仍是每 Tick 跟随。
- 为什么否掉"客户端本地算 + eps + Sid 并列"（曾讨论）：要调 eps、要对齐时间基准，边界仍可能翻边；房主下发把翻边风险降为 0，带宽 ~24B/s 可忽略。
- 残留：成员中心滞后房主 ~RTT+插值 ⇒ "创建瞬间取 center"仍差 `速度×RTT`（比原方案好一个量级，可接受）。
- ⚠ 客户端**必须插值**，不能把 2Hz 的包当每帧值（否则生成物位置会台阶跳）。

### 2.3b 战斗开始的创建位置（已核查）
- **本机玩家**：`BattleRoleManager.GetStartPoint()` = `Medivac` 标记物体的固定变换 ⇒ **两端一致** ✅
- **盟友（Friend）**：`NetFriendBridge.NextSpawnPos` = `StartPoint` 标签（战斗场景多半没有 ⇒ 退化为"本机玩家位置"）+ **本机视角序号**偏移 ⇒ **两端不一致**，但 `_firstPoseSent` 让**首条位姿带 `Teleport=true`** ⇒ 一个包间隔内**吸附**到真实位置（KCP 可靠有序 ⇒ 必到）。
- ⇒ 家具"创建时算 `SyncId` 并缓存"**安全**（家具位置来自场景/地图，不来自玩家位置）。
- ⚠ 唯一要警惕：将来若有物件是**"相对玩家位置"创建**的，战斗开始那一瞬会踩到盟友的短暂偏差 ⇒ 要改成相对确定性锚点创建。

### 2.4 昼夜：改为"每次从墙钟重算"
- `TimeProgressionModule`（`DayNightSystem/Modules/TimeProgressionModule.cs`）：初始 `CurrentAngle = (60*now.Minute + now.Second) % 1800 / 1800 * 360`（**墙钟锚点**），但之后 `CurrentAngle += speed * deltaTime`（累加）⇒ 会漂。
- 改法：`Tick` 里每次从墙钟重算（不累加）⇒ 真正的静态同步，两端只剩机器时钟差（NTP <1s，30 分钟周期可忽略）。

### 2.5 不同步（已拍板排除）
- 团灭判负倒计时（`OnWipeFailCountdown/Cancel`）：血量已同步、算法一致 ⇒ **各端本地判定**。
- 战备授权（`OnRequestAuthorize`/`OnAuthorizeAirdrop`）：**每人独立** ⇒ 不同步。
- UI / 输入 / 本机视角 / 本机经验 / `OnActorSpeech`(远端播放入口) / `OnBulletHit` / `OnUnitHit` / `OnNoise` / `OnPathRequest` / `OnUnitPosChange` / `OnMissionStateChange`(纯 UI 显隐)。

### 2.6 本地收口（不占消息号）
- `GlobalEventBus.OnPlayMeetSpeech` → 在 `PlayerSpeechManager` 里**转成** `BattleEventBus.PlayerSpeech`（复用已有的 4030/4031）⇒ **网络层零改动**，`Reload/Help/Thank/Evacuate/Install` 全部自动同步。

### 2.7 键的选择（讨论结论）
| 对象 | 键 |
|---|---|
| 敌人 | `NetId`（`Actor.Id` 对敌人不唯一；`NetId` 就是为此造的） |
| NPC / 场景单位 / 凯伊 | `Actor.Id`（实测大厅 NPC Id = `Noa`/`Mika`/`Hare`/`Aris`，唯一） |
| 玩家/盟友 | `Sid` |
| 家具 | `FNV1a(Id + 位置量化)`（缓存） |
| 任务 | `MissionBase.netOrder` |
- ⚠ 曾想"统一成一个 NetId"（`EnemyMove`→`ActorMove`）：合并会让两套键空间（host 自增号段 vs 字符串 Id）打架。
  若要统一，做法是**把"同步键"显式化**（`MoveKey{int NetId; string Id;}` 或前缀字符串 `"E{n}"`/`"S{id}"`），**不要**为它建 `Id→NetId` 映射表（那就比直接用 Id 更绕）。
