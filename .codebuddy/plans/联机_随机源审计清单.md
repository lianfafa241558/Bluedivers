## 1. 判定规则（怎么分类）

对每个随机消费点问 3 个问题：

| 问题 | 是 → | 否 → |
| --- | --- | --- |
| ① 它发生在**初始化窗口内**（`BattleRandom = new(seed)` → `IsStartBattle = true`）？ | 进【种子区】候选 | 进【快照区】 |
| ② 它的结果会影响**玩法**（位置/数量/构成/状态），不只是外观？ | 必须两端一致 | 【无所谓】 |
| ③ 它的两端一致性**现在实现了**（源可下发 + 消费顺序可锁）？ | ✅ 可用 | ⚠ 先修再用 |

**窗口定义**（证据 `BattleManager.cs:164/111` → `:209/153`）：

```
BattleRandom = new(taskCfg.seed)   ← 窗口开始
  ├─ InitTerrain()                 （仅 Init() 路径，多帧）
  ├─ MissionCont.Init + WaitForInitialization   （多帧）
  ├─ WaveCont.Awake（消费静态流！）
  ├─ RandomWeather()               （BattleRandom）
  ├─ yield return null
  ├─ GameState = Game
  ├─ yield return null             ← ⚠ 危险间隙（见 A5）
  ├─ DrainInitQueue()              （CreatOOPart/CreateSupple/CreateBuilding）
  └─ IsStartBattle = true          ← 窗口结束
```

## 8. 验证方法（三段，缺一不可）

### ① 静态断言（防回归，写进提交前检查）
- 维护一份**白名单**：允许在窗口内消费 `BattleRandom` / 静态流的 `文件:行` 集合 = 本文 §4 的表。
- 脚本（Python，沿用项目惯例）扫描全仓 `BattleRandom` / `RandomUtils.` / `UnityEngine.Random`，**落在白名单外的新增点直接报错** ⇒ 防止以后有人往窗口里塞随机。

### ② 运行期探针（最有效，能 100% 定位漂移）
- 开发构建下把 `RandomUtils` 的 `random` 与 `BattleManager.BattleRandom` 包一层 `CountingRandom`（记录 `序号 / 调用点(用 [CallerMemberName]+行号 或堆栈) / 返回值`）。
- 初始化结束（`IsStartBattle = true`）时，两端各导出 `init_random_trace.txt`。
- **判据：窗口内两端的 trace 必须完全一致**（逐行 diff）。不一致的第一行就是漂移源。

### ③ 产物指纹比对（业务侧验收）
初始化结束时打印一份指纹，两端比对必须逐字段相同：
天气 / 任务点清单(id+位置) / 兴趣点清单 / 场景点清单 / 欧帕兹清单 / 补给清单 / 波次模板 id / 地形与 NavMesh 抽样点（如走 A3 的场景地形路线，抽样也要一致）。

## 10. 决策落地（2026-10-06 用户拍板）

### 10.0 先核实："加入房间时同步种子"确实存在 —— 但它只喂了一条流

| 调用点 1：成员收到开局广播 | `TeamNetBridge.cs:161` `team.SetSeed(ntf.Seed)` | 同上 |

### 10.6 A2 追加分析：**"都用北京时间 ⇒ 表就一致" —— 条件成立，但比想象的窄**

> ⚠⚠ **本节结论已被 §10.10 修正**：我当时**漏算了 `TaskManager.Update` 的自动刷新具有"自愈"作用**。在"两端都在运行"的前提下，30 分钟窗口其实能自愈；真正的坑是**当前的 2 分钟版本**。请以 **§10.10** 为准，本节保留作分析过程。

先回答用户的问题：**时钟一致时，"同一个 30 分钟桶内"确实会生成完全相同的 `TaskCfgs`**（`new System.Random(seed)` 同种子 ⇒ 同序列）。但有 **3 个缺口**：

| # | 缺口 | 证据 |
| --- | --- | --- |
| 1 | **窗口绑的是"启动那一刻"，不是"开局那一刻"**。`CreatAllTask()` 在 `TaskManager.Init()`（`TaskManager.cs:141`）执行，而 `TaskManager` 挂在常驻的 `GameRoot` 上 ⇒ 种子取**各自启动时的墙钟**。玩家 9:50 开游戏、10:20 才入房 ⇒ 他用的是 9:30 桶，房主 10:05 开 ⇒ 10:00 桶 ⇒ **表不同**（这恰恰是最常见的情形：游戏开很久才联机） | `TaskManager.cs:141` + `TaskManager.cs:180` |
| 2 | ⚠ **每小时 `:00` / `:30` 会自动重建整表**（新发现）：`TaskManager.Update()`（`:156-171`）里 `if (now.Minute == 0 \|\| now.Minute == 30) → CreatAllTask()`。⇒ 一端跨过刷新点、另一端没跨 ⇒ 表不同。例：A 13:29 启动（桶 13:00）、B 13:31 启动（桶 13:30） | `TaskManager.cs:156-171` |
| 3 | **时钟本身**：`DateTime.Now` 是**本地时间**。NTP 同步精度通常够，但①非北京时区/系统时区设错 ②长期关机后的漂移 ③手动改过时间 ⇒ 都可能跨桶。概率小但**完全静默** | `TaskManager.cs:178` |

**量化**：把两端启动时刻视作随机，同桶概率 ≈ `1 - E[Δt] / 30min`。若平均相隔 10 分钟 ⇒ **约 1/3 概率不在同一桶**。而**当前 2 分钟版本几乎必然不一致**（那是你为单机测试设的）。

**结论与建议（分两步，第一步极便宜）**：

1. **第一步（强烈建议）：让不一致变得"不静默"** —— 开局广播里带一个 **`TaskCfgFingerprint`**（`main` / `extra[]` / `nestCount[]` / `seed` / `scale` / `enable` 的 hash），成员比对，不一致就**明确报错**"任务表不同步，请重启游戏后重新入房"。
2. **第二步：不一致就自动修复** —— 用房主下发的内容**只替换本局那一项** `TaskCfgs[area, taskIndex]`（不动大厅列表）。
3. ⚠ **关键澄清**：这一步发生在"**开局广播到达**"时，而那时玩家**已经联网**了 ⇒ **它不受"开机时没联网"的限制**（那个约束只影响 `CreatAllTask()` 在启动时取种子这件事）。所以"先试跨窗口、失败再升级"是安全的推进路线。

> 📌 另外记一条**待确认风险**：`:00/:30` 的自动重建若发生在**战斗中**，`CreatAllTask` 会 `TaskCfgs[i,u] = new TaskCfg{...}` 替换数组元素。若 `nowTask.taskCfg` 持有旧对象引用则本局安全；若 `SetTask` 之后还会回读 `TaskCfgs` ⇒ 本局配置会被**中途换掉**。上线前需确认。

### 10.7 A5 追加分析：**"实例化顺序一致" vs "房主权威" 两条路都行，建议按类别分工**

> 用户明确：只是问问，不马上实施。

**路 1 · 让实例化顺序一致（继续用种子）** —— 现状是"半有序"：

- ✅ `BattleManager._initQueue` 是 **FIFO**（`BattleManager.cs:50-51`），drain 顺序 = 入队顺序（`:347-355`）
- ❌ 但**入队顺序**取决于 Unity 对各组件 `Awake`/`Start` 的调用顺序 —— 同帧多对象**不受契约保证**（实际通常按场景序列化顺序，但不可依赖）
- 要做到真有序，需三件事：① **统一出口**（所有窗口内生成点都走 `EnqueueInit`，禁止自己在 `Update` 里生成）；② **入队即带 `sortKey`**（用稳定身份：世界坐标量化哈希 / 场景层级路径哈希），drain 前排序；③ **参数来自确定性流**（不是全局静态流，见 §4 的 B11/B12）
- 代价：每个生成点补 `sortKey`，且以后新增点必须守约定（需脚本检查防回归）

**路 2 · 房主权威（推荐给"离散 spawn"）** —— 房主生成后广播**静态生成物清单**（prefabId + 位置 + 朝向 + 参数 + NetId），成员不再自己生成：

- ✅ **一次性解决三件事**：顺序、随机、身份（NetId）—— 因为"顺序问题"根本不存在了
- ✅ 机制**与位置同步计划的 Spawn 事件是同一套**，不需要新系统
- 成本：一次性包。数量估算：兴趣点 `6 ~ 2√CameraSize`、场景点 `20 ~ 3√CameraSize`（`MissionController.cs:301/318`）+ 欧帕兹/补给/建筑若干 ⇒ 按 ~20B/项、100 项 ≈ 2KB ⇒ 2 个包，可接受
- ❌ **它不能替代种子**：地形（高度图 + 几千棵树 + 覆盖石）是"数学生成"，不可能逐实例广播

**⇒ 建议的分工（这就是"哪个更好"的答案）**

| 类别 | 方案 | 理由 |
| --- | --- | --- |
| 地形 / 植被 / 覆盖石 | **种子派生流**（§10.3） | 数学生成、数量巨大（几千棵），无法广播 |
| 任务点 / 兴趣点 / 场景点 | **种子派生流** | 由 `MissionController` 协程按固定顺序生成 ✓，顺序天然确定 |
| 欧帕兹 / 补给 / 建筑（**离散 spawn**） | **房主权威清单** | 靠各组件 `Awake`/`Start` 自发入队，顺序不受契约保护；数量有限、只发一次 |
| 敌人 / 空投（运行期） | **房主权威 Spawn 事件** | 与位置同步计划同一套机制，直接复用 |

⇒ 这样"让顺序一致"的改造面被压到最小：**只需把"离散 spawn"那一类改成房主权威**，其余全靠确定性流。

## 10.10 第三轮：A2 自愈机制（**修正 §10.6**）+ UTC 桶 + A5 身份结论

### 10.10.1 回答「A 13:29 启动，13:30 会刷新吧？」—— ✅ **对，而且这一条推翻了我上一轮的悲观结论**

`TaskManager.Update()`（`:156-171`）的时序：

```
13:29 → now.Minute == 29 ⇒ else 分支 ⇒ hasTriggeredThisMinute = false
13:30 → now.Minute == 30 ⇒ 触发 CreatAllTask()，hasTriggeredThisMinute = true   ← ✅ 会刷新
13:31 → Minute == 31 ⇒ else ⇒ 复位为 false（为下一个半点做准备）
```

**关键推论（我上一轮漏掉的）**：`hasTriggeredThisMinute` 的复位机制让刷新**每个 :00/:30 必发生一次**，而 `CreatAllTask()` 算出的种子是**当前桶**的值。于是：

| 客户端 | 启动 | 启动时种子 | 13:30 刷新后 |
| --- | --- | --- | --- |
| A | 13:29 | 桶 `13:00` | → 桶 `13:30` ✅ |
| B | 13:31 | 桶 `13:30` | — |
| **结果** | | | **两者一致** ✅ |

⇒ **自动刷新 = 自愈机制**：只要两端**都在运行**，跨过任意一个 :00/:30 就会收敛到同一个桶。**30 分钟窗口下，两端在运行状态就能自动对齐**（我上一轮"约 1/3 概率失败"的估计是错的，因为忽略了这条自愈路径——特此修正）。

**反过来，正是当前的 2 分钟版本在制造问题**：`now.Minute / 2 * 2` 让**启动时**算出的值与**:00/:30 刷新时**算出的值不同（13:05 启动 ⇒ 桶 4；刷新时 ⇒ 桶 0/30），而刷新只在 :00/:30 发生 ⇒ 两端在任意时刻都可能不一致，直到下一个半点的"巧合重合"。**这正是"2 分钟只为单机测试"必须改回 30 分钟的真正原因**。

### 10.10.2 回答「用时间戳呢？」—— ✅ 方向对，但要"**UTC + 量化到桶**"

| 做法 | 效果 |
| --- | --- |
| `DateTimeOffset.UtcNow.ToUnixTimeSeconds()` | ✅ **消除时区依赖**（`DateTime.Now` 跨时区必崩，这是当前公式的真实缺陷） |
| 直接拿时间戳当种子 | ❌ **不行** —— 时间戳编码了**精确启动时刻**，两端必然不同；必须**向下量化成桶** |
| 量化：`bucket = UtcNow.ToUnixTimeSeconds() / 1800`（30min） | ✅ 与我方"30 分钟窗口"功能等价（北京是 UTC+8 整小时时区 ⇒ 桶边界仍落在本地 :00/:30） |

**推荐实现**（顺带修掉当前公式的隐患）：

```csharp
// 唯一随机源：UTC 30 分钟桶
static long CurrentBucket() => DateTimeOffset.UtcNow.ToUnixTimeSeconds() / 1800;
TaskRandom = new System.Random(unchecked((int)CurrentBucket()));
```

- ⚠ `System.Random` 构造只吃 **int32** ⇒ 别直接传 `long`（用 `unchecked((int)…)` 或哈希）
- ✅ 额外收益：当前公式 `Month*100 + Day + Hour*100 + window` **不是单射**（例：`Hour=13,Month=10` 与 `Hour=11,Month=12` 都可能得 2300）⇒ 存在"不同时刻意外撞成同一个表"的隐患，换成桶 id 就没这问题

**刷新条件也建议一起改**：从"`Minute == 0 || Minute == 30`"改成"**桶变化检测**"

```csharp
var bucket = CurrentBucket();
if (bucket != _lastBucket) { _lastBucket = bucket; _pendingRefresh = true; }
if (_pendingRefresh && GameRoot.GameState == GameStateEnum.Bridge) { CreatAllTask(); _pendingRefresh = false; }
```

这一改同时解决 3 件事：
1. **漏拍自愈**：笔记本**休眠**从 13:29 睡到 13:41，`Minute` 已不是 0/30 ⇒ 原逻辑**永远不刷新**（一直停在旧桶）；桶变化检测睡醒立刻补刷 ✅
2. **只在舰桥刷新**（你的第 3 点）✅ —— 战斗中不换表，回舰桥补刷
3. **与"自愈"兼容**：战斗期间大厅表变化**本来就无所谓**（本局配置在开局时已落到 `nowTask`），所以"战斗中不刷"不会破坏对齐 —— 两支队伍回到舰桥时都会对齐到当前桶 ✅

> 附带小提醒：回到舰桥补刷会把**大厅任务列表**换掉。若玩家正开着`SelectMapWnd`（它展示的正是 `TaskCfgs`），列表会突然变。原逻辑（:00/:30 刷新）本来也是这行为，不算新增问题，但可以考虑"刷新后通知选图界面重绘"。

### 10.10.4 A5 回答「按坐标哈希排序 `_initQueue`，能保证自增 id 同步吗？」—— ⚠ **能对齐"被排序那部分"的顺序，但保证不了 `IndexID` 同步**，而且**不建议往这个方向做**

**为什么保证不了**（三条硬理由）：

1. **`IndexID` 在 `Instantiate` 时就分配了**，不是 drain 时：`Actor.Awake()` 里 `indexID = GlobalIndexID++`（`Actor.cs:206/24`）⇒ 排序 `_initQueue` 只对"**在队列 action 里 Instantiate**"的那些对象（欧帕兹/补给/建筑）有效。
2. **创建路径不止队列一条**：玩家（`RoleManagerBase.cs:34`）、任务实体（`MissionController.cs:171`）、敌人（`WaveManager.cs:255`、`RobotWave/ZergWave`）、召唤物（`UnitSkill_Summoner.cs:23`）、环绕装甲（`UnitSkill_OrbitArmor.cs:71`）**全都直接 `Instantiate`** ⇒ 它们与队列对象**争抢同一个全局计数器**，顺序依旧不可控。
3. **`GlobalIndexID` 是 `static` 且跨局不清零**（`Actor.cs:24` 只在声明处初始化）⇒ 只要**任意一端历史上多创建过哪怕 1 个 Actor**（比如先打过一局单机、或某一局多刷了一个兵），之后所有 ID **永久错位**。

**而且不该做**：`Actor.IndexID` 已经是**本地身份**，被当键在用 ——
- `Actor.Equals(IActor obj) => obj.IndexID == IndexID`（`Actor.cs:109`）、`GetHashCode() => indexID.GetHashCode()`（`:113-116`）
- ⇒ 强行"跨端同步 IndexID"= 要求所有端**历史 Actor 总数与创建顺序永远一致**，这在"动态刷兵 + 死亡"的游戏里不可能维持。

**⇒ 建议：`IndexID` 保持"本地身份证"不动；跨端身份用新的 `NetId`（房主分配）并存**（见位置同步计划 §3.2）。`NetId` 只挂在需要同步的实体上，与 `IndexID` 互不干扰。

**你的思路仍然有价值，但用途要换一下**：排序 + 坐标哈希可以保证"**生成物集合及其参数一致**"（即"谁在哪生成了什么"一致），这是**静态布局确定性**要的东西；只是别指望它顺带解决 `IndexID`。用它时注意三点：

1. **必须先量化再哈希**：`Vector3` 浮点直接哈希不稳（两端可能差 1e-6）⇒ `Hash(RoundToInt(pos.x*100), RoundToInt(pos.y*100), RoundToInt(pos.z*100))`
2. **坐标重合要有 tie-breaker**：两个物体同坐标 ⇒ 哈希相等，排序不稳定 ⇒ 追加次级键（prefab 名 / 场景层级路径）
3. **排序会改变随机消费顺序**：所以必须**先把这些生成点的参数改成"各自确定性流"**（§4 的 B11/B12 → `BattleRandom`），再排序 —— 否则排序本身就会把随机线打乱

### 10.11 A5 定稿：排序键用 `PEVector3`（⭐ 最优解）+ `IndexID` 不要同步 + 不要重置

#### 10.11.1 分类细化：**"顺序由代码固定"的那部分根本不需要排序**

| 类别 | 顺序是否确定 | 需要做什么 |
| --- | --- | --- |
| `MissionController` 生成的任务点 / 兴趣点 / 场景点（`:171 / :309 / :326`） | ✅ **由协程代码固定**（不是 `Awake` 顺序） | **不需要排序**，只需参数来自确定性流 |
| `CreatOOPart` / `CreateSupple` / `CreateBuilding`（场景预置组件自发 `EnqueueInit`） | ❌ 取决于 Unity 的 `Awake` 顺序 | **需要排序** + 确定性流 |
| 玩家 | ❌ 各端只创建自己 | 房主 `NetId` |
| 敌人 / 召唤物 / 环绕装甲 | ❌ 运行期 | 房主 Spawn 事件 + `NetId` |

⇒ "`_initQueue` 内用哈希排序"实际只需覆盖**第二行那 3 类组件**，比想象的小得多。

#### 10.11.2 ⚠ "加入房间时重置 `GlobalIndexID`" —— **危险，不建议**

- **大厅里确实有存活的 `Actor`**：`RoleManagerBase.Start`（`:34`）`Instantiate("Prefabs/BattleBase/Player")` → `PlayerController`（带 `Actor`）；`BridgeRoleManager.Start`（`:31-59`）还额外 Instantiate 一批展示模型。
- ⇒ 加入房间时把 `GlobalIndexID` 归零，之后新建的 Actor 会从 0 开始，**与大厅里仍存活的那批撞号**；而 `Actor.Equals`（`:109`）与 `GetHashCode`（`:113-116`）**正是按 `IndexID` 比较** ⇒ `Dictionary<IActor,…>` / `HashSet` 会互相顶掉，属极难定位的一类 bug。
- 相对安全的时机只有"**旧 Actor 已全部销毁**"时（新战斗场景加载后），但**重置也无法解决同步问题**（见下）。
- 🟢 **而且没有动机**：`int` 要涨到 21 亿才溢出（实际不可能）；跨端身份改用 `NetId` 之后，`IndexID` 只需保证**本地唯一**，而它天然单调唯一 ✓。
- ⇒ **结论：不重置。** 若将来真要做，只允许在"新战斗场景已加载 + 断言 `ActorsManager.Actors` 为空"时执行。

#### 10.11.3 ⭐ 排序键：`Vector3 → PEVector3` 是**最优解**（比我上轮的 `RoundToInt(pos*100)` 更正统）

`Assets/Plugins/PEMaths/PEMaths.dll` 的 `PEVector3` 给了两个关键能力：

| 能力 | 证据 | 用途 |
| --- | --- | --- |
| **定点量化** | `PEVector3(Vector3 v)` 构造里 `x = (PEInt)v.x`（`:86-91`）；`PEInt` 是带 `ScaledValue(long)` 的定点类型 | **天然抗浮点抖动**：两端同一位置的微小浮点差异被量化吸收 ✓ |
| **权威整数出口** | `CoverLongArray()` → `long[3] { x.ScaledValue, y.ScaledValue, z.ScaledValue }`（`:146-149`） | **直接拿三个 long 做键**，无需自己定精度 ✓ |

⚠ **两个坑**：

1. **别用 `PEVector3.GetHashCode()`** —— 它是 `x.GetHashCode() + y.GetHashCode() + z.GetHashCode()`（`:166-169`），**加法可交换 ⇒ 碰撞极多**（(1,2,3) 与 (3,2,1) 同哈希）⇒ 排序键必须自己 mix（如 `FNV` 逐轴混合）。
2. **别用 `RawVector3Int` / `RawInt`** —— `RawInt` 是**整数部分**（`:84`）⇒ 米级精度太粗，会把相近物体压成同键；用 `ScaledValue`。

> 待确认（实现前看一眼 `PEInt.cs`）：`(PEInt)float` 的转换是截断还是四舍五入、量化单位是多少（若为 0.001m 则完全够用）。此外位置**恰好落在量化边界**时两端可能分到相邻格——概率极低，且若位置本身来自确定性计算就不会发生。

#### 10.11.4 ⭐ prefab 身份：思路对，但**别用字符串哈希**

| 做法 | 评价 |
| --- | --- |
| `name.GetHashCode()` | ❌ **绝对不行** —— `string.GetHashCode()` 在 .NET Core / .NET 5+ 是**随机化**的（跨进程不同），Mono 行为也不能依赖 ⇒ 换一次进程键就变，排序直接失效 |
| 自己写确定性字符串哈希（FNV-1a / `h = h*31 + c`） | ✅ 可行 |
| **用整数 prefabId**（prefab 在 `MapData_SO` / 配置数组里的索引，或枚举 key） | ✅✅ **推荐** —— 完全绕开字符串哈希问题 |
| `GameObject.name` | ❌ 常带 `(Clone)` / 实例后缀 ⇒ 必须用**资产名或整数 id**，不是实例名 |

**⇒ 建议排序键（三级，保证全序）**：

```
orderKey = ( Mix(CoverLongArray[0..2]),   prefabId(int),   层级路径哈希(可选) )
```

- 用稳定的 LINQ `OrderBy`（稳定排序）+ 最后一级 tie-breaker 兜底
